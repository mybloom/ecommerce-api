# Product 애그리거트

> **범위**: 큐레이션 오픈마켓 MVP — 사용자 관점

---

## A. 행위

> **책임**: 판매되는 상품의 정보를 표현하고, 판매 상태와 재고를 관리한다. 사용자가 탐색하고 구매하는 단위로서, 브랜드에 소속되며 좋아요의 대상이 된다.

### UC-1. 상품 목록 조회

**목적**  
사용자가 판매 중인 상품들을 둘러보며 관심 상품을 발견한다.

**입력**

| 파라미터 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| memberId | MemberId | 선택 | 없음 | 로그인한 회원 (X-MEMBER-ID 헤더). 없으면 비로그인 |
| brandId | BrandId | 선택 | 없음 | 단일 브랜드 필터. 없으면 전체 |
| sort | ProductSort | 선택 | `latest` | 정렬 기준 |
| page | Int | 선택 | 0 | 페이지 번호 (0부터) |
| size | Int | 선택 | 20 | 페이지 크기 |

**정렬 기준 (`ProductSort`)**
- `latest` — 개시 일시(`openedAt`) 내림차순
- `priceDesc` — 가격 높은순
- `likeDesc` — 좋아요 많은순
- 목록에 없는 값이 오면 `latest`로 처리한다 (참고: Product-005)

**출력**

상품 요약 목록과 페이징 메타.

상품 요약 정보:
- 상품 ID, 상품명, 대표 이미지
- 브랜드 ID, 브랜드명
- 가격, 좋아요 수, 품절 여부
- 내가 좋아요 눌렀는지 (`isLiked`). 비로그인이면 항상 `false`

페이징 메타:
- 전체 개수, 현재 페이지, 전체 페이지 수, 다음 페이지 존재 여부

**좋아요 여부 정책** (참고: Product-006, Product-007)
- 비로그인: 모든 상품의 `isLiked`가 `false`다. 좋아요 여부는 조회하지 않는다
- 로그인: 내가 좋아요한 상품은 `true`, 아닌 상품은 `false`
- 헤더의 회원이 실제로 있는지는 확인하지 않는다. 없는 회원이면 좋아요 기록이 없으므로 모두 `false`

**필터 정책**
- `status == ON_SALE`인 상품만 노출 (`OFF_SALE`, `HIDDEN`은 제외)
- 품절 상품(`stockQuantity == 0`)은 노출됨
- 소속 브랜드가 `ACTIVE`가 아닌 상품은 제외 (참고: brand.md Brand-001) 
- `brandId`로 걸렀는데 브랜드가 없거나 `ACTIVE`가 아니면 200 + 빈 목록

**처리 정책** (참고: Product-005)
- Product와 Brand를 단일 쿼리로 조인해 상품 요약을 구성한다
- 판매 상태·브랜드 상태 필터는 조회 시점 WHERE 절에서 수행한다 (페이징 정확성 보장)
- 도메인 엔티티를 거치지 않고 조회 전용 모델(`ProductSummary`)로 직접 받는다
- 로그인했으면 조회한 페이지의 상품 id로 좋아요 여부를 한 번에 조회해 UseCase에서 조합한다 (Product-006)

**정렬 정책**
- 사용자가 선택한 정렬 기준을 그대로 적용
- 품절 상품도 동일 정렬에 포함됨 (참고: Product-002)
- 정렬 결과 안정성을 위해 2차 정렬 키로 `productId` 사용
    - 예: `likeDesc` → `ORDER BY likeCount DESC, productId DESC`

### UC-2. 상품 단건 조회

**목적**  
사용자가 목록에서 상품을 눌러 해당 상품의 상세 정보를 확인한다.

**입력**

- `productId` : ProductId — 조회할 상품 식별자

**출력**

상품 상세 정보:
- 상품 ID, 상품명, 상세 설명, 대표 이미지
- 브랜드 ID, 브랜드명
- 가격, 품절 여부, 좋아요 수
- 판매 상태, 개시 일시

**필터 정책**
- `status == ON_SALE`인 상품만 조회 가능. `OFF_SALE`, `HIDDEN`은 "찾을 수 없음"(404) 응답
- 소속 브랜드가 `ACTIVE`가 아니면 "찾을 수 없음"(404) 응답 (참고: brand.md Brand-001)
    - 현재 구현에서는 브랜드 조회 단계에서 발생함

**미결 사항**
- 로그인 사용자 한정 "내가 좋아요 눌렀는지"는 아직 응답에 포함되지 않음 (ProductLike 미개발, 참고: C.3)

### 도메인 이벤트

> 현재 단계에서는 이벤트 도입 보류. 향후 필요 시점에 추가.

향후 후보:
- `ProductRegistered` — 상품 등록됨
- `ProductSoldOut` — 상품 품절됨
- `ProductRestocked` — 상품 재입고됨

## B. 구조

> 위 행위를 가능하게 하는 내부 구성. 애그리거트 루트와 값 객체, 외부 관계로 이루어진다.

### B.1. Product : Entity, Aggregate Root

#### 속성

- `id` : Long — 식별자
- `name` : String — 상품명
- `description` : String — 상세 설명
- `representativeImage` : ImageUrl — 대표 이미지
- `brandId` : Long — 소속 브랜드 (ID 참조)
- `price` : Money — 판매 가격
- `stockQuantity` : StockQuantity — 재고 수량
- `likeCount` : Int — 좋아요 수 (캐시)
- `status` : ProductStatus — 판매 상태
- `openedAt` : ZonedDateTime — 상품 개시 일시

**불변식**
- `price`는 0 이상
- `likeCount`는 0 이상

**파생 속성**
- `isSoldOut` : Boolean — `stockQuantity == 0`

#### 행위

- `increaseLikeCount()` : 좋아요 수를 1 증가시킨다 (ProductLike 추가 시 호출, 참고: Product-003)
- `decreaseLikeCount()` : 좋아요 수를 1 감소시킨다 (ProductLike 삭제 시 호출, 참고: Product-003)
- `putOffSale()` : 판매 상태를 `OFF_SALE`로 변경한다
- `hide()` : 판매 상태를 `HIDDEN`으로 변경한다
- `isVisibleToUser()` : Boolean — `ProductStatus.isVisibleToUser()`에 위임한다

> 그 외 행위(상품 등록, 가격 변경, 판매 상태 변경 등)는 해당 유스케이스가 정의될 때 함께 추가한다.

---

### B.2. ProductStatus : Value Object

판매 상태를 나타내는 열거형.

#### 속성

- `ON_SALE` — 판매 중 (사용자에게 노출됨)
- `OFF_SALE` — 판매 중지 (노출되지 않음)
- `HIDDEN` — 숨김 (노출되지 않음, 운영상 사유)

#### 행위

- `isVisibleToUser()` : Boolean — 사용자에게 노출 가능한 상태인지 반환한다. `ON_SALE`만 `true`

---

### B.3. StockQuantity : Value Object

재고 수량을 나타내는 값 객체. 

#### 속성

- `value` : Int — 재고 수량 (0 이상)

**불변식**
- `value`는 0 이상

#### 행위

- `isSoldOut()` : Boolean — 재고가 0인지 반환한다

### B.4. 다른 애그리거트와의 관계

- **Brand** ← `brandId`로 참조 (단방향, ID 참조)
- **ProductLike** → `ProductLike`가 `productId`로 이 애그리거트를 참조함
    - 좋아요 추가/삭제 시 `Product.likeCount` 동기 업데이트 (참고: Product-003)

## C. 설계 결정

> 확정된 결정과 보류된 결정을 함께 모은다. 보류된 항목이 결정되면 C.2 → C.1로 이동한다.

### C.1. 확정된 결정

> **왜 이런 선택을 했는지** 보존한다. 결정은 누적될 뿐 수정되지 않는다.

#### Product-002. 품절 상품 정렬 정책 보류
- **일시**: 2026-05-07
- **결정**: 품절 상품을 정렬에서 후순위로 보내지 않고, 일반 정렬에 포함시킴.
- **이유**:
    - 초기 상품 수가 적어 정책 효과가 미미함
    - 리팩토링 비용이 낮음 (정렬 쿼리 한 곳만 수정)
- **영향**: `ORDER BY` 절에 품절 여부 분기 없음.
- **재검토 시점**: 상품 수가 충분히 많아져 품절 상품이 사용자 탐색을 방해할 때, 또는 관련 사용자 피드백 발생 시.

#### Product-003. 좋아요 카운트는 캐시 컬럼으로 보관
- **일시**: 2026-05-07
- **결정**: `Product.likeCount`를 컬럼으로 보관. 좋아요 추가/삭제 시 동기적으로 업데이트.
- **이유**: `likeDesc` 정렬에 사용되므로 매번 COUNT 쿼리는 비효율적.
- **영향**:
    - `ProductLike` 추가/삭제 트랜잭션에서 `Product.likeCount`도 함께 변경
    - 진실의 원천은 `ProductLike` 테이블, `likeCount`는 캐시
- **관련 애그리거트**: ProductLike (참고: ProductLike.md)
- **재검토 시점**: 좋아요 트래픽 증가로 동시성 이슈가 발생하거나 카운트 불일치 문제가 생길 때 → 이벤트 기반 비동기 업데이트로 전환.

#### Product-004. `decreaseLikeCount()`는 0에서 멈춘다
- **일시**: 2026-08-25
- **결정**: `likeCount`가 0일 때 `decreaseLikeCount()`가 호출되면 예외를 던지지 않고 0을 유지한다.
- **이유**:
    - Product-003이 `likeCount`를 **캐시**로, ProductLike 테이블을 진실의 원천으로 정했다
    - 캐시가 어긋난 상태에서 예외를 던지면 같은 트랜잭션이 롤백되어 **사용자가 좋아요를 영영 취소하지 못한다.** 데이터 불일치의 대가를 사용자가 치르게 된다
    - `StockQuantity.of` / `Money.of`가 음수에 예외를 던지는 것과 판단이 다른 이유는, **그 둘은 사용자 입력이고 `likeCount`는 파생된 캐시**이기 때문이다. 입력 검증은 막아야 하지만 캐시 드리프트는 흡수하는 편이 낫다
- **영향**:
    - B.1의 `likeCount >= 0` 불변식은 예외가 아니라 clamp로 지켜진다
    - 캐시 드리프트가 조용히 감춰진다. 정합성이 중요해지면 별도 보정 배치나 모니터링이 필요하다
- **재검토 시점**: 좋아요 수 불일치가 실제로 관측될 때 → 보정 수단을 먼저 마련하고 나서 예외 전환을 검토.

#### Product-005. 상품 목록은 조인 + 조회 전용 모델로 조회
- **일시**: 2026-09-17
- **결정**: 상품 목록은 product와 brand를 조인해 `ProductSummary`로 받는다. 알 수 없는 `sort`는 `latest`로 처리한다.
- **이유**:
    - 비활성 브랜드 필터를 조회 뒤 메모리에서 걸면 한 페이지에 `size`보다 적게 담기고 전체 개수도 틀린다
    - ACTIVE 브랜드 id를 먼저 모아 `IN`으로 넘기는 방식보다 쿼리가 한 번이고, 좋아요한 상품 목록(ProductLike UC-3)과 모양이 같다
    - `sort` 오타로 요청 전체를 실패시키기보다 기본 정렬로 응답한다. `page`/`size`를 보정하는 규칙과 방향을 맞췄다
- **영향**:
    - product Repository 구현이 brand 테이블을 안다 (조회 전용, 쓰기는 없음)
    - 클라이언트는 `sort` 오타를 응답으로 알아차리기 어렵다
- **재검토 시점**: 조인 비용이 성능 테스트에서 문제로 확인될 때.

#### Product-006. 목록의 좋아요 여부는 페이지 단위로 따로 조회해 UseCase에서 조합한다
- **일시**: 2026-09-17
- **결정**: 상품 목록 쿼리에 product_like를 조인하지 않는다. 한 페이지를 조회한 뒤, 로그인했으면 그 페이지의 상품 id들로 좋아요한 id만 한 번 조회해 `isLiked`를 채운다. 헤더의 회원 존재는 확인하지 않는다.
- **이유**:
    - 좋아요 여부는 필터·정렬에 쓰이지 않아 페이징 정확성과 무관하다. 조회 뒤에 붙여도 한 페이지의 개수와 전체 개수가 틀리지 않는다
    - 조인하면 비로그인 요청까지 같은 쿼리 모양을 공유해야 하고, 상품 Repository가 좋아요 테이블까지 알게 된다
    - 추가 쿼리는 페이지당 한 번(`IN`, 최대 `size`개)이라 비용이 작다
    - 회원 존재 확인은 좋아요 API와 같게 하지 않는다. 확인해도 결과가 모두 `false`로 같고, 조회마다 회원 쿼리가 늘어난다
- **영향**:
    - `ProductUseCase.getProducts`가 `ProductService`와 `ProductLikeService`를 조합한다
    - 비로그인 응답에는 `isLiked` 필드가 없다 (Jackson `NON_NULL`)
- **재검토 시점**: 목록 정렬이나 필터에 좋아요 여부가 필요해질 때 (예: "내가 좋아요한 상품만").

#### Product-007. 비로그인 사용자의 좋아요 여부는 `false`로 응답한다
- **일시**: 2026-09-17
- **결정**: 비로그인 요청에서도 `isLiked` 필드를 항상 내려주고 값은 `false`로 둔다. Product-006의 "비로그인 응답에는 `isLiked` 필드가 없다"를 대체한다.
- **검토한 선택지**:

| | 비로그인이면 `false` | 비로그인이면 필드 생략 (null) |
|---|---|---|
| 응답 모양 | 로그인 여부와 무관하게 같다 | 로그인 여부에 따라 필드가 있다가 없다 |
| 타입 | `boolean` | `@Nullable Boolean` — Result·Response·테스트까지 null 허용이 번진다 |
| 클라이언트 처리 | 값 두 가지 (`true`/`false`) | 상태 세 가지 (`true`/`false`/없음) |
| "좋아요 안 함"과 "알 수 없음" 구분 | 구분되지 않는다 | 응답만 보고 구분된다 |
| 로그인 사용자인데 헤더가 빠진 버그 | 모두 `false`로 조용히 나간다 | 필드가 빠져 조금 더 눈에 띈다 (오류는 아님) |

- **이유**:
    - 로그인 여부는 요청에 인증 정보를 싣는 클라이언트가 이미 안다. "알 수 없음"을 응답으로 알려줄 필요가 거의 없다
    - 화면은 비로그인이면 빈 하트를 보이고 누르면 로그인으로 보내는 경우가 흔하다. `false`가 그 표시와 그대로 맞는다
    - 이 프로젝트는 null 허용을 예외로 표시하고 빌드로 지킨다(decisions/0001). 필요 없는 null 허용을 응답 계약에 두지 않는다
- **감수한 것**:
    - 응답만 보고는 "좋아요 안 함"과 "비로그인"을 구분할 수 없다
    - 로그인 사용자의 헤더가 빠지는 버그가 생겨도 응답이 정상처럼 보인다
- **영향**:
    - `ProductSummaryResult`·`ProductSummaryResponse`의 `isLiked`는 `boolean`
    - 비로그인이면 UseCase가 `ProductLikeService`를 부르지 않고 `false`를 넣는다
- **재검토 시점**: 클라이언트가 응답만으로 로그인 여부를 판단해야 하는 요구가 생길 때 (예: 서버 렌더링 캐시를 로그인 여부와 무관하게 공유할 때).
