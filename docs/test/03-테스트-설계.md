# 03. 테스트 설계 — 결제

> **STLC 3단계.** [요구사항 분석](./01-요구사항-분석.md)의 REQ-PAY 15개와 F-1~F-7, [테스트 계획서](./02-테스트-계획서.md)의 레벨 전략을 **실행 가능한 테스트 케이스**로 바꾼다.
> 이 문서의 케이스 ID가 이후 이슈, 테스트 이름, RTM(04)의 키가 된다.

---

## 1. 설계 방법

| 기법 | 쓰는 곳 | 이유 |
|---|---|---|
| 상태 전이 | 2절 | `OrderStatus`, `PaymentStatus`가 상태 기계다. 허용·금지 전이를 빠짐없이 센다 |
| 결정 테이블 | 3절 | 결제수단 × PG 응답 × 콜백 도착 여부의 조합마다 기대 결과가 다르다 |
| 오류 추정 | 4절 | 요구사항 분석에서 찾은 결함 후보(F-1~F-7)와 경험상 약한 지점을 직접 겨냥한다 |
| 규제·보안 | 5절 | 카드번호 노출, 콜백 위조 등 체크리스트 항목(계획서 5절)을 케이스로 만든다 |

### 표기 규칙

| 항목 | 값 |
|---|---|
| 케이스 ID | `TC-PAY-nnn`. 2절 001~, 3절 020~, 4절 050~, 5절 070~ |
| 위치 | **JUnit** = `apps/commerce-api` (내부 로직, 동시성), **PW** = Playwright API 테스트 (블랙박스, 조립된 서버) |
| 우선순위 | **P0** = 돈·재고가 직접 틀어짐 (출시 차단 후보), **P1** = 주요 흐름·정합성, **P2** = 보조·회귀 |
| 근거 | REQ-PAY-nn, F-n(결함 후보), 공백 n순위(공백 분석 2절) |
| PG 응답 | 시스템 테스트(PW)는 WireMock으로 고정한다 (계획서 D-1). 실제 pg-simulator는 야간 E2E만 |

> 2절의 도메인 전이 케이스는 기존 118개 결제 테스트와 겹칠 가능성이 높다. **Day 3 시작 때 기존 테스트와 대조해 겹치는 케이스는 새로 쓰지 않고 ID만 연결한다.**

## 2. 상태 전이

### 2.1 상태 기계 (코드 기준)

```
Order:   PENDING ──confirm──▶ AWAITING_PAYMENT ──pay──────────────▶ PAID
            │                        │
            └─markOrderFailed─▶ ORDER_FAILED     └─markPaymentFailed─▶ PAYMENT_FAILED

Payment: PENDING ──approve──▶ APPROVED
            │
            └─fail────────▶ FAILED
```

종결 상태(`ORDER_FAILED`, `PAID`, `PAYMENT_FAILED`, `APPROVED`, `FAILED`)에서 나가는 전이는 없다. 금지 전이는 `CONFLICT`를 던진다.

### 2.2 허용 전이

| 케이스 | 전이 | 기대 | 요구사항 | 위치 | 우선순위 |
|---|---|---|---|---|---|
| TC-PAY-001 | Order `PENDING → AWAITING_PAYMENT` | 라인 확정, 총액 = 라인 합계 | REQ-PAY-04 | JUnit | P2 |
| TC-PAY-002 | Order `PENDING → ORDER_FAILED` | 상태 변경 | REQ-PAY-04 | JUnit | P2 |
| TC-PAY-003 | Order `AWAITING_PAYMENT → PAID` | `paidAt` 기록 | REQ-PAY-01, 03 | JUnit | P1 |
| TC-PAY-004 | Order `AWAITING_PAYMENT → PAYMENT_FAILED` | 상태 변경 (재고 복원은 3절에서 확인) | REQ-PAY-02 | JUnit | P1 |
| TC-PAY-005 | Payment `PENDING → APPROVED` | `approvedAt` 기록 | REQ-PAY-01, 03 | JUnit | P1 |
| TC-PAY-006 | Payment `PENDING → FAILED` | `failureReason` 기록 | REQ-PAY-02 | JUnit | P1 |

### 2.3 금지 전이

| 케이스 | 시도 | 기대 | 요구사항 | 위치 | 우선순위 |
|---|---|---|---|---|---|

| TC-PAY-009 | `AWAITING_PAYMENT`가 아닌 주문(PENDING, ORDER_FAILED, PAID, PAYMENT_FAILED)에 결제 요청 | 409, Payment 행이 생기지 않음 | REQ-PAY-05 | JUnit + PW | P1 |
| TC-PAY-010 | `PAID` 주문에 같은 수단으로 재결제 요청 | 409, 포인트·재고 변화 없음 | REQ-PAY-05 | PW | P1 |

### 2.4 (Order, Payment) 조합 불변식

두 상태 기계는 따로 움직이지만 **짝이 맞아야 한다.** 모든 결제 시나리오(3, 4절) 끝에서 아래 표를 확인한다.

| Order | Payment | 판정 |
|---|---|---|
| `AWAITING_PAYMENT` | 없음 | 허용 (결제 전) |
| `AWAITING_PAYMENT` | `PENDING` | 허용 (콜백 대기) |
| `PAID` | `APPROVED` | 허용 |
| `PAYMENT_FAILED` | `FAILED` | 허용 |
| 그 외 모든 조합 | | **금지.** 발견 즉시 Critical 후보 |

| 케이스 | 내용 | 요구사항 | 위치 | 우선순위 |
|---|---|---|---|---|
| TC-PAY-012 | 3, 4절 시나리오마다 종료 시점에 위 표의 허용 조합인지 확인하는 공용 검증 | REQ-PAY-01~03, 06 | JUnit(통합), PW(DB 읽기 헬퍼, D-2) | P0 |
| TC-PAY-013 | 카드 승인은 `transactionKey` 필수, 포인트 승인은 `transactionKey`가 있으면 거부 | REQ-PAY-01, 03 | JUnit | P2 |
| TC-PAY-014 | 실패 확정 시 사유가 비어 있으면 거부 (사유 없는 실패 금지) | REQ-PAY-02 | JUnit | P2 |
