## 3. 테스트 접근

### 3.1 레벨별 전략

| 레벨 | 검증 대상 | 도구 | 위치 | PG | 언제 실행 |
|---|---|---|---|---|---|
| 단위 | 도메인 규칙, 재시도·서킷 정책 | JUnit 5, AssertJ | 앱 저장소 (기존) | 가짜 객체 | PR마다 |
| 통합 | 트랜잭션 경계, 동시성, DB 제약 | JUnit 5, Testcontainers(MySQL), CountDownLatch | 앱 저장소 (**보강**) | Mock | PR마다 |
| 시스템 (API) | 배포된 앱을 HTTP로만: 정상·실패·재처리·보안 | **Playwright (TypeScript)** | **별도 자동화 프로젝트** (신규) | **WireMock 컨테이너** (결정적) | main 머지마다 |
| E2E | 요청 → 실제 PG 처리 → 콜백 → 종결 왕복 | Playwright | 별도 자동화 프로젝트 | **실제 pg-simulator** (비결정적) | nightly + 수동 |
| 탐색적 | 명세에 없는 실패 | 수동, 차터 기반 | — | 둘 다 | Day 3·5 |

### 3.2 자동화 전략: 무엇을 어디서 테스트하는가

**원칙: 코드 내부를 알아야 검증할 수 있는 것은 앱 저장소의 JUnit, 사용자·외부 시스템이 보는 그대로 검증할 것은 Playwright.**

| 기준 | 앱 저장소 JUnit | Playwright 자동화 프로젝트 |
|---|---|---|
| 관점 | 화이트박스·그레이박스 | 블랙박스 |
| 대상 | 트랜잭션, 락, 동시 실행 타이밍 | 배포된 API, 서비스 간 연동 |
| 테스트 더블 | Mockito, 가짜 게이트웨이 | 컨테이너 단위 대역 (WireMock) |
| 작성 주체 | 개발자 + SDET | SDET (개발자도 기여 가능하게 구조화) |
| 이번 스프린트 추가분 | 동시 결제(다른 주문), 동시 콜백 | 위조 콜백, PG 장애 흐름, 전체 왕복, 민감정보 |

**Playwright를 고른 이유**

- **UI 도구이지만 API 테스트에 쓴다.** Playwright는 브라우저 자동화 도구로 알려져 있으나 `APIRequestContext`로 브라우저 없이 HTTP 요청을 직접 보낼 수 있다. 이 프로젝트는 화면이 없는 
  백엔드 API이므로 UI 기능은 쓰지 않고 API 테스트 기능만 쓴다. 
결제 화면이 생기면 같은 프레임워크를 확장한다
- **대안과 비교했다.** RestAssured, pytest + requests, Postman도 API 테스트만 보면 충분하다. Playwright를 택한 것은 병렬 실행·트레이스·리포트·태그가 한 도구에 있어 별도 조합이 필요 없기 때문이다
- **트레이드오프.** 앱(Java)과 언어가 달라 테스트 코드와 앱 코드를 함께 읽기 어렵다. 이 비용은 블랙박스 경계가 강제되는 이점과 맞바꾼 것이며, 내부 동작이 필요한 검증은 JUnit에 둔다

### 3.3 결정한 사항

| 결정 | 내용 | 근거 |
|---|---|---|
| D-1. PG 대역 | 시스템 테스트는 **WireMock 컨테이너**로 PG 응답을 시나리오별로 고정한다. 실제 pg-simulator는 E2E(nightly)에서만 쓴다 | pg-simulator 결과가 무작위라(40% 500, 30% 실패) 같은 테스트가 실행마다 다르다 (Q-E1). 판정에 쓰는 테스트는 결정적이어야 한다 |
| D-2. 결과 관측 | 주문 상세 API가 없어(F-7) **읽기 전용 DB 검증 헬퍼**를 Playwright 프로젝트에 둔다. API가 생기면 교체한다 | 블랙박스 원칙의 예외. 예외인 이유와 교체 조건을 코드 주석과 이 문서에 남긴다 |
| D-3. 콜백 재현 | 시스템 테스트는 PG 콜백을 **테스트가 직접 보낸다.** 실제 콜백 왕복은 E2E에서 본다 | 콜백 내용과 타이밍(중복, 위조, 지연)을 테스트가 통제해야 하기 때문 |
| D-4. 결함 처리 | 결함은 재현 테스트와 함께 버그 이슈로 등록한다. 재현 테스트는 수정 전까지 `test.fail()`(Playwright) / `@Disabled("BUG-#")`(JUnit)로 둔다 | 수정되면 테스트가 알려 주고, 판정서에서 미해결 결함을 테스트로 추적한다 |

## 5. 규제·보안 체크리스트

> 토이 프로젝트 기준으로 결제 서비스에 통상 요구되는 항목을 테스트 관점에서 옮긴 것이다. 실제 적용 범위는 회사 컴플라이언스 기준을 따른다.

| ID | 항목 | 관련 기준 | 테스트 방법 | 요구사항 |
|---|---|---|---|---|
| SEC-1 | 카드번호를 평문으로 저장하지 않는다 | PCI DSS (카드 데이터 보호) | 결제 후 DB 스키마·데이터 확인 | REQ-PAY-12 |
| SEC-2 | 카드번호가 응답·로그에 평문으로 남지 않는다 | PCI DSS (표시 시 마스킹) | 결제 실행 후 응답 본문·앱 로그 검사 | REQ-PAY-12 |
| SEC-3 | 결제 결과는 PG가 보낸 것만 반영한다 | 거래의 무결성 | 위조 콜백 시나리오 | REQ-PAY-13 |
| SEC-4 | 다른 회원의 주문은 결제할 수 없고 존재도 노출하지 않는다 | 접근 통제 | 타 회원 주문 결제 → 404 | REQ-PAY-11 |
| SEC-5 | 결제 금액을 요청으로 바꿀 수 없다 | 거래의 무결성 | 요청에 금액 필드를 실어 보냄 | REQ-PAY-04 |
| SEC-6 | 외부 시스템 오류 메시지를 사용자에게 노출하지 않는다 | 정보 노출 최소화 | PG 거절 시 응답 본문 확인 | REQ-PAY-08 |
| SEC-7 | 테스트에 실제 개인정보·카드정보를 쓰지 않는다 | 개인정보 보호 | 데이터 팩토리 규칙, 리뷰 | — |

## 7. 진입·종료 기준

### 7.1 진입 기준 (테스트 실행을 시작해도 되는가)

- [ ] 대상 커밋의 기존 테스트가 모두 통과한다 (`./gradlew test`)
- [ ] system-test compose가 한 명령으로 기동되고 헬스체크를 통과한다
- [ ] 테스트 설계 문서의 케이스에 ID와 레벨이 지정되어 있다
- [ ] 시드 데이터와 테스트 데이터 팩토리가 준비되어 있다

### 7.2 종료 기준 (출시 판정을 내릴 수 있는가)

- [ ] 계획한 테스트 케이스 실행률 100%
- [ ] **리스크 최우선 영역(6.1)의 테스트가 모두 실행되었다** (통과가 아니라 실행. 결함이면 결함으로 판정에 반영)
- [ ] 요구사항 REQ-PAY-01 ~ 15가 모두 하나 이상의 테스트에 연결되었다 (RTM)
- [ ] 회귀: 기존 테스트 전체 통과
- [ ] 발견한 결함이 모두 이슈로 등록되고 Severity·Priority가 정해졌다
- [ ] CI에서 단위·통합·시스템 테스트가 자동 실행된다

### 7.3 판정 기준

| 판정 | 조건 |
|---|---|
| **Go** | 미해결 Critical·Major 결함 0건 |
| **Conditional Go** | 미해결 Major가 있으나 우회책(기능 플래그, 운영 절차)이 있고 PO가 승인 |
| **No-Go** | 미해결 Critical 결함이 1건 이상, 또는 리스크 최우선 영역을 실행하지 못함 |

## 8. 결함 관리

| Severity | 정의 | 예 |
|---|---|---|
| Critical | 돈이 잘못 움직이거나 보안이 뚫린다 | 결제 없이 주문 완료, 포인트 차감 유실 |
| Major | 데이터 정합성이 깨지거나 주요 흐름이 막힌다. 우회책 없음 | 재고 이중 복원, 결제 영구 `PENDING` |
| Minor | 기능은 동작하나 일부가 틀리거나 불편하다 | 실패 안내 문구와 실제 행동 불일치 |
| Trivial | 표시·문구 수준 | 오탈자 |

- 등록: `.github/ISSUE_TEMPLATE/bug-report.md` (영어)
- 상태: Open → In Progress → Fixed → Retest → Closed / Reopened, 또는 Deferred(다음 스프린트) / Rejected
- 이관: 수정이 설계 결정을 바꾸는 결함(F-1, F-6 등)은 개발팀 이관으로 기록하고, 간단한 결함만 직접 수정한다
