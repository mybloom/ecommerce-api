## 1. 규칙을 먼저 세우고 시작했습니다

`.claude/skills/` 에 규칙 문서를 두고
Claude Code 가 작업 종류에 따라 스스로 꺼내 쓰게 했습니다.

| 스킬 | 담는 것 |
|---|---|
| `architecture-rules` | 레이어 의존성, 패키지 네이밍, 예외 처리, 테스트 컨벤션 |
| `tfd-workflow-outside-in` | 새 기능 절차 — 밖에서 안으로(API 진입점부터) |
| `test-effectiveness` | 작성한 테스트가 정말 결함을 잡는지 검증 |
| `git-conventions` | 커밋 메시지, 커밋 분리, 브랜치별 문서 소유 |
| `pr-history` | 기능을 마친 뒤 PR 브랜치를 다시 구성 |
| `pr-description` | PR 설명에 무엇을 남기고 무엇을 걷어낼지 |


## 2. 기능을 레이어 단위로 개발하고 레이어마다 테스트를 먼저 작성했습니다

관통하는 원칙은 넷입니다.

- **진입 레이어부터 작성해서 안으로 들어갑니다.** interfaces → application → domain →
  infrastructure 순서로 코드를 작성합니다. 
- **레이어마다 Red → Green 을 돕니다.** 테스트를 먼저 쓰고 그 테스트가 통과하는 최소 구현만 합니다
- **아래 레이어는 계약만 만듭니다.** Controller 부터 내려가면서 개발하므로 지금 만드는 층이 아직 없는 아래층을 호출하게 됩니다. 그래서 아래층에는 불리는 데 필요한 것(메서드 시그니처와 DTO)만 먼저 두고 본문은 `UnsupportedOperationException` 으로 막아둡니다
- **레이어를 끝낼 때마다 멈춰서 확인받습니다.** 자동으로 다음 레이어로 넘어가지 않습니다

### 2.1 도메인 명세 — 무엇을 만들지 먼저 적습니다

코드보다 명세가 먼저입니다. `docs/도메인모델/` 에 해당 도메인 문서를 쓰고,
없거나 불명확하면 질문해서 채웁니다.

- **A. 행위** — 유스케이스별 입력 · 처리 · 결과와 실패 조건
- **B. 구조** — 엔티티 · 값 객체의 속성, **상태별 불변식 표**, 각 객체가 갖는 행위
- **C. 설계 결정** — `Order-004` 처럼 번호를 붙인 판단과 근거

### 2.2 Interface Layer — API 표면을 확정합니다

- 컨트롤러 슬라이스 테스트를 먼저 씁니다
- **요청·응답 DTO**, **API 명세 인터페이스**, **컨트롤러** 를 만듭니다
- 컨트롤러가 호출하는 유스케이스는 시그니처만 두고 본문을 스켈레톤으로 막습니다
- **E2E 테스트를 `@Disabled` 로 먼저 작성해둡니다.** 완성 목표를 코드에 남기는 용도입니다

### 2.3 Application Layer — 유스케이스 본문을 채웁니다

유스케이스는 **여러 도메인 서비스와 트랜잭션을 순서대로 엮어 하나의 기능을 완성하는 자리**입니다.

- 유스케이스 통합 테스트를 역시 `@Disabled` 로 써 두고 유스케이스를 구현합니다
- 도메인 서비스는 아직 계약만 만듭니다

### 2.4 Domain Layer — 엔티티와 도메인 서비스를 나눠서 만듭니다

아래와 같이 **두 번에 나눠 작성합니다.**

- **1) 엔티티 · 값 객체** — 이 객체가 어떤 행위를 갖고 **각 행위가 무엇을 보장해야 하는지**를
  테스트로 먼저 정합니다. 정상 결과뿐 아니라 규칙을 어겼을 때 어떻게 거절하는지,
  실패한 뒤 어떤 상태로 남는지까지 정합니다. 그다음 그 테스트가 통과하는 최소 구현만 합니다.
- **2) 도메인 서비스 · Repository 인터페이스** — Repository 를 목으로 두고 테스트를 쓴 뒤
  2.3 에서 남긴 스켈레톤을 걷어냅니다

### 2.5 Infrastructure Layer — 여기서 스프링 컨텍스트가 온전해집니다

- domain 이 인터페이스로 선언해 둔 것을 **실제 기술로 구현합니다.** 
- 예) 주문에서는 Repository, 비밀번호 해싱(`PasswordEncoder`), 외부 결제 게이트웨이
- 구현 빈이 생겨야 관통 경로가 이어지므로, **이 단계에서 처음으로 스프링 컨텍스트가 온전해집니다.**
- **Repository 테스트는 가릴 것만 씁니다.** 기준은 *"이 메서드의 쿼리 동작이 메서드명만 보고 명확한가"* 입니다. 명확하면 Spring Data JPA 를 믿고 쓰지 않고, 모호하면 씁니다 — `@Query` · QueryDSL · 네이티브 쿼리 · 복잡한 조인 · 벌크 연산 · 잠금(`@Lock`)

### 2.6 E2E 봉합 — 막아둔 테스트를 전부 켭니다

- 2.2 와 2.3 에서 `@Disabled` 로 둔 테스트를 풉니다. **이때 처음으로 전 구간이 실제로 검증됩니다.**
- 스켈레톤이 남아 있으면 500 에러가 발생하므로 이 단계에서 전수 확인합니다.

### 이 방식이 감수하는 것

1. **중간 단계에는 실행되는 검증이 거의 없습니다.** 아래가 스켈레톤이라 대부분의 테스트가
   `@Disabled` 입니다. 안전망이 마지막 단계에 몰립니다
2. **Red 를 유보합니다.** 레이어를 가로지르는 테스트는 Red 로 돌릴 수조차 없습니다.
   2.3 의 완료 조건이 "이 단계에서 통과시킬 수 있는 테스트는 없다" 인 것이 그 때문입니다
3. **그 구간을 목으로 메우지 않습니다.** 검증할 동작이 아직 없는데 목을 배선하면
   남는 것은 배선 확인뿐입니다

## 3. 테스트가 진짜로 결함을 잡는지 따로 검증했습니다

**테스트 성공은 결함이 없다는 뜻이 아닙니다.** 아무것도 단언하지 않는 테스트는 결함이 있어도 통과합니다 — 결함을 "없음" 으로 보고하는 false negative 입니다.
커버리지로도 드러나지 않습니다. 

그래서 **결함을 일부러 심어** 테스트가 실패하는지 봤습니다. 심은 결함은 답을 아는 양성이므로,
이때 통과한 테스트는 false negative를 낸 것입니다. 그런 테스트는 테스트를 수정하였습니다. 

```java
// 두 상수가 똑같이 1L 이라 인자가 뒤바뀌어도 드러나지 않던 것
public static final Long DEFAULT_MEMBER_ID = 11L;
public static final Long DEFAULT_PRODUCT_ID = 22L;

// save(any()) 로 호출 여부만 보던 것을 값까지 확인하도록
ArgumentCaptor<ProductLike> captor = ArgumentCaptor.forClass(ProductLike.class);
verify(productLikeRepository).save(captor.capture());
```

### 도메인 레이어는 pitest 가 자동으로 검증합니다

**결함을 손으로 심으면 원복을 빠뜨릴 위험이 남습니다.** pitest 는 **메모리에 올린 바이트코드**에만
변이를 넣습니다. 

pitest 가 도메인 레이어를 맡습니다. 가드 조건 반전과 상태를 바꾸는 메서드 본문 비우기를
전수로 심습니다. 도메인 테스트는 스프링 컨텍스트 없이 돌아 Docker 없이 20초에 끝납니다.

같은 타입 인자 교환과 `catch` 블록 변환, 그리고 Testcontainers 위에서 도는
`application` · `interfaces` 는 **직접 심어 볼 수 있게 남겨 두었습니다.**

## 4. 규칙 준수를 모델의 판단에 두지 않고 결정적 검사를 사용했습니다.

- 규칙을 문서와 스킬에만 적어 두면 **비결정적입니다.** 모델이 읽을 수도 건너뛸 수도 있습니다. 
- **규칙이 확정되면 검사로 구현합니다.** 검사는 모델의 의사와 무관하게 실행되고 같은 입력에 항상 같은 판정을 냅니다.

| 검사 | 무엇을 막나 | 어떻게 걸리나 |
|---|---|---|
| **NullAway** | null 안전성 위반 | 컴파일이 실패합니다 |
| **훅** | 레이어 건너뛰기와 의존성 역행, `@Embedded` 매핑 누락 | 파일을 쓰는 순간 **이유와 함께 되돌립니다** |
| **pitest** | 결함을 놓치는 테스트 | 심은 변이가 `SURVIVED` 로 남습니다 |
