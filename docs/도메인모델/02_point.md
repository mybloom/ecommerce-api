# Point 애그리거트

> **범위**: 큐레이션 오픈마켓 MVP — 사용자 관점

---

## A. 행위

> **책임**: 회원이 보유한 포인트 잔액을 표현하고 관리한다. 충전을 통해 잔액을 늘리고, 주문/결제 등에서사용을 통해 잔액을 차감하는 책임을 진다. 포인트 사용잔액의 무결성(음수 불가, 부족 시 사용 
> 불가)을 보장한다.

### UC-1. 포인트 충전

**목적**  
로그인한 회원이 자신의 포인트 잔액을 늘린다.

**입력**

- `memberId` : MemberId — 충전 대상 회원 (X-MEMBER-ID 헤더에서 추출)
- `amount` : Money — 충전 금액

**출력**

충전 결과 
- `balance` : Money - 갱신된 잔액 
- `amount` : Money - 충전된 금액

**전제 조건**
- 사용자는 로그인 상태여야 함
- 충전 금액은 양수여야 함

**처리 정책**
- 회원의 Point는 회원가입 시점에 함께 생성되어 항상 존재함을 가정 (참고: Point-001)
- 충전 금액이 0 이하이면 예외 처리

**도메인 협력**
- `point.charge(amount)` 호출하여 잔액 증가

---

### UC-2. 내 포인트 조회

**목적**  
로그인한 회원이 자신의 현재 포인트 잔액을 확인한다.

**입력**

- `memberId` : MemberId — 조회 대상 회원 (X-MEMBER-ID 헤더에서 추출)

**출력**

- 현재 포인트 잔액 (`Money`)

**전제 조건**
- 사용자는 로그인 상태여야 함

**처리 정책**
- 회원의 Point는 회원가입 시점에 잔액 0으로 함께 생성되므로, 조회 시 항상 존재함을 가정 (참고: Point-001)
- Point 잔액을 그대로 반환

**도메인 협력**
> 단순 조회 유스케이스로, 도메인 객체에 호출되는 행위 없음.

---

### 도메인 이벤트

> 현재 단계에서는 이벤트 도입 보류.

향후 후보:
- `PointCharged` — 포인트가 충전됨
- `PointUsed` — 포인트가 사용됨

## B. 구조

> 위 행위를 가능하게 하는 내부 구성. 애그리거트 루트와 외부 관계로 이루어진다.

### B.1. Point : Entity, Aggregate Root

#### 속성

- `id` : Long — 식별자
- `memberId` : Long — 소유 회원 ID 참조. Unique 제약으로 한 회원당 하나의 Point (참고: Point-002)
- `balance` : Money — 현재 포인트 잔액

**불변식**
- `balance`는 0 이상 (`Money` 타입 자체가 음수를 허용하지 않음으로 보장)
- `memberId`는 시스템 내에서 유일 (한 회원당 하나의 Point — 참고: Point-002)

#### 행위

- `createInitial(memberId)` : Point — 초기 잔액 0(`Money.ZERO`)으로 새 Point를 생성한다 (정적 팩토리)
- `charge(amount)` : void — 포인트 잔액을 `amount`만큼 증가시킨다. `amount`가 양수가 아니면 예외
- `use(amount)` : void — 포인트 잔액을 `amount`만큼 차감한다. 잔액이 부족하거나 `amount`가 음수면 예외

> `use()`는 본 컨텍스트의 유스케이스에서 직접 호출되지 않으며, 향후 주문/결제 유스케이스에서 호출될 예정이다.

---

### B.2. 다른 애그리거트와의 관계

- **Member** ← `memberId`로 참조 (단방향, ID 참조)
    - 회원 도메인은 별도 컨텍스트, ID로만 참조
    - 한 회원당 하나의 Point가 매핑됨 (참고: Point-002)
- 추후 주문/결제 도메인이 `point.use(amount)`를 호출하여 포인트를 사용할 예정

---

## 공통 값 객체 — Money

> Money는 Point 애그리거트만의 값 객체가 아니라 시스템 전반에서 공통으로 사용되는 값 객체이다 (Product의 `price`, 주문 금액 등에서도 동일하게 사용). 본 문서에서는 Point에서 사용하는 관점만 간략히 정리하며, 상세 정의는 별도 공통 문서를 참조한다.

**핵심 특징**
- 음수가 될 수 없음 (생성 시 검증)
- `Money.ZERO` 상수 제공
- 불변(immutable) 값 객체
- 주요 행위: `add`, `subtract`, `isZero`, `isPositive`, `isLessThan`

## C. 설계 결정

> 확정된 결정과 보류된 결정을 함께 모은다. 보류된 항목이 결정되면 C.2 → C.1로 이동한다.

### C.1. 확정된 결정

> **왜 이런 선택을 했는지** 보존한다. 결정은 누적될 뿐 수정되지 않는다.

#### Point-001. 회원가입 시 Point를 함께 생성
- **일시**: 2026-05-07
- **결정**: 회원이 가입하는 시점에 잔액 0의 Point를 함께 생성한다. 회원과 Point의 생명주기를 동기화한다.
- **이유**:
    - 모든 회원이 항상 Point를 가진다는 단순한 모델 — 도처의 분기 제거
    - 충전/조회 시점마다 Point 존재 여부를 확인할 필요 없음
    - "Point가 없는 회원"이라는 모호한 상태가 존재하지 않음
- **영향**:
    - Member 도메인의 회원가입 유스케이스가 Point 도메인의 `Point.createInitial(memberId)`를 호출
    - 충전(UC-1), 조회(UC-2)에서 Point 존재 여부 분기 불필요
    - 회원가입 시 Member 생성과 Point 생성은 동일 트랜잭션에서 처리되어야 함
- **관련 애그리거트**: Member (참고: Member.md UC-1)
- **재검토 시점**: 회원가입과 Point 생성을 분리해야 할 비즈니스 요구사항이 생길 때 (예: 게스트 회원, Point 도메인의 별도 라이프사이클 관리).

#### Point-002. 한 회원당 하나의 Point만 존재
- **일시**: 2026-05-07
- **결정**: 회원과 Point는 1:1 관계로, 한 회원은 하나의 Point 인스턴스만 가진다. `memberId`에 UNIQUE 제약을 부여한다.
- **이유**:
    - 사용자에게 "포인트 잔액"은 단일 개념 — 여러 잔액을 보여주면 혼란
    - MVP 단계에서 단순화 (적립 단위별 분리, 만료 정책 등 복잡도 회피)
    - 충전/사용 시 "어느 Point에 적용할지" 결정할 필요 없음
- **영향**:
    - DB 레벨에서 `member_id`에 UNIQUE 인덱스 필요
    - 충전/사용 시 회원의 단일 Point만 다루면 됨
- **재검토 시점**: 포인트 종류 분리(예: 일반 포인트, 프로모션 포인트, 만료 포인트)가 필요해질 때.

#### Point-003. Money 값 객체로 잔액의 무결성 보장
- **일시**: 2026-05-07
- **결정**: Point의 잔액(`balance`)은 `Money` 값 객체로 표현한다. `Money`는 음수를 허용하지 않으며, 산술 연산도 자체적으로 안전하게 수행한다.
- **이유**:
    - 잔액의 음수 방지를 타입 자체가 보장 
    - `Long`을 직접 다룰 때 발생하는 단위 혼동, 음수 계산 실수 방지
    - 다른 도메인(상품 가격, 주문 금액 등)과 일관된 표현
- **영향**:
    - Point는 `balance: Long`이 아닌 `balance: Money`를 보유
    - `charge()`, `use()`는 `Money` 타입의 인자를 받음
    - Money는 공통 값 객체로 여러 도메인이 공유

#### Point-004. 잔액 부족 시 use()는 예외 처리
- **일시**: 2026-05-07
- **결정**: `point.use(amount)` 호출 시 잔액이 부족하면 예외(`CONFLICT`)를 던진다. 부분 차감이나 false 반환 같은 처리를 하지 않는다.
- **이유**:
    - 잔액 부족은 도메인 규칙 위반 — 명시적인 실패가 안전
    - 호출 측에서 try-catch로 분기하는 게 boolean 반환 방식보다 명확
    - 부분 차감은 결제 도메인의 책임이 흐려질 위험
- **영향**:
    - 호출 측에서 잔액 사전 확인 또는 예외 처리 필요
    - 주문/결제 흐름에서 포인트 사용 가능 여부를 사전에 검증하는 패턴 권장
