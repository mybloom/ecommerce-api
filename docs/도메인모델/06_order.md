# Order 애그리거트

> **범위**: 큐레이션 오픈마켓 MVP — 사용자 관점

---

## A. 행위

> **책임**: 주문 요청을 먼저 접수해 중복 요청을 걸러내고, 상품을 검증해 재고를 확보한 뒤 결제 가능한 상태로 만든다. 그 금액을 실제로 받아내는 일은 별도 요청으로 Payment가 맡는다 (참고: Order-003, 07_payment.md). 주문이 확정된 뒤에는 상품 정보가 바뀌어도 주문 내용은 바뀌지 않는다.

### API 엔드포인트

| METHOD | URI | 설명 | 대응 UC |
|---|---|---|---|
| POST | `/api/v1/orders` | 주문 요청 | UC-1 |
| GET | `/api/v1/orders` | 유저의 주문 목록 조회 | UC-2 |
| GET | `/api/v1/orders/{orderNumber}` | 단일 주문 상세 조회 | UC-3 |

> 결제는 이 엔드포인트들에 포함되지 않는다. 주문이 `AWAITING_PAYMENT`가 된 뒤 `POST /api/v1/payments`를 따로 호출한다 (참고: Order-003, 07_payment.md UC-1).

### UC-1. 주문 요청

**목적**
로그인한 회원이 상품과 수량을 지정해 주문을 접수하고, 재고를 확보해 결제할 수 있는 상태로 만든다.

**입력**

| 파라미터 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `memberId` | MemberId | 필수 | 주문하는 회원 (X-MEMBER-ID 헤더에서 추출) |
| `idempotencyKey` | String | 필수 | 중복 요청 식별자 (Idempotency-Key 헤더에서 추출, 참고: Order-004) |
| `items` | List&lt;OrderItem&gt; | 필수 | 주문 항목 목록. 1개 이상 |
| `items[].productId` | Long | 필수 | 주문 대상 상품 |
| `items[].quantity` | Int | 필수 | 주문 수량. 1 이상 |

> `OrderItem`은 요청 DTO의 타입이지 도메인 객체가 아니다. `productId`와 `quantity`만 갖는다.
> 이것으로 서버가 상품을 조회해 상품명과 단가를 채운 `OrderLine`을 만든다 (참고: Order-001, B.2).
> 상품 자체가 아니라 "상품 + 수량"이므로 `Product`라는 이름을 쓰지 않는다. 도메인의 `Product`와도 이름이 겹친다.

> 주문 금액은 요청에 포함하지 않는다 (참고: Order-002).
> 결제 수단도 이 요청에 포함하지 않는다. 결제 요청에서 선택한다 (참고: 07_payment.md UC-1).

**출력**

| 필드 | 타입 | 설명 |
|---|---|---|
| `orderNumber` | String | 주문번호. 이후 조회와 결제에 쓰는 식별자다 (참고: Order-011) |
| `status` | OrderStatus | 정상 처리 시 `AWAITING_PAYMENT` |
| `totalAmount` | Long | 서버가 계산한 결제 예정 금액 |
| `orderedAt` | ZonedDateTime | 주문 접수 시각 |
| `isDuplicatedRequest` | Boolean | 같은 `idempotencyKey`로 이미 접수된 주문을 그대로 돌려준 경우 `true` (참고: Order-004) |

> 주문 라인 상세는 응답에 포함하지 않는다. 필요하면 UC-3으로 다시 받는다.
> 클라이언트는 이 `orderNumber`로 결제를 요청한다 (참고: 07_payment.md UC-1).
> 내부 식별자 `id`는 응답에 담지 않는다 (참고: Order-011).

> `isDuplicatedRequest`가 `true`여도 **응답 코드는 200이고 나머지 필드는 정상 주문과 같다.**
> 중복 요청은 오류가 아니라 멱등하게 처리된 정상 요청이기 때문이다 (참고: Order-004).
> 클라이언트가 "방금 내가 만든 주문인지, 이전 요청이 만든 주문인지"를 구분해야 할 때 쓴다.

**전제 조건**
- 사용자는 로그인 상태여야 함
- `Idempotency-Key` 헤더가 있어야 함
- 주문 항목이 1개 이상이어야 함
- 각 상품은 `ON_SALE` 상태이고 소속 브랜드가 `ACTIVE`여야 함 (참고: Order-009)
    - `OFF_SALE`, `HIDDEN` 상품이나 비활성 브랜드의 상품은 "찾을 수 없음"(404) 응답
- 각 상품의 재고가 주문 수량 이상이어야 함

**처리 정책**

접수와 확정을 **서로 다른 트랜잭션**에서 수행한다 (참고: Order-004).

**T1. 접수** — 커밋된다

1. `idempotencyKey`로 기존 주문을 찾는다. **있으면 그 주문의 현재 상태를 그대로 반환하고 끝낸다.** 새 주문을 만들지 않는다 (참고: Order-004)
2. 없으면 주문번호를 채번하고(참고: Order-011), `Order.draft(memberId, orderNumber, idempotencyKey)`로 주문을 `PENDING` 상태로 저장한다
    - 이 시점의 주문은 "누가 주문을 시도했다"는 사실만 담는다. 라인도 금액도 아직 없다

**T2. 확정** — 커밋된다

3. 각 `productId`로 상품을 조회하고 노출 조건을 검증한다 — `ProductService.retrieve()` + `BrandService.retrieve()` 조합을 그대로 재사용 (`ProductLikeProcessor`와 동일한 방식, 참고: Order-009)
4. 각 상품의 재고를 주문 수량만큼 **차감한다.** 재고가 부족하면 `Product.decreaseStock()`이 `CONFLICT`를 던진다 (참고: Order-005)
5. 상품명과 단가를 스냅샷한 `OrderLine`을 구성한다 (참고: Order-001)
6. `Order.confirm(lines)`로 총액을 확정하고 상태를 `AWAITING_PAYMENT`로 전이한다

**T3. 확정 실패 시** — T2가 실패했을 때만 수행하며, 별도로 커밋된다

7. `Order.markOrderFailed()`로 상태를 `ORDER_FAILED`로 전이한다
8. T2에서 발생한 예외를 그대로 클라이언트에 전파한다 (4xx)

> **재고는 되돌릴 필요가 없다.** T2가 단일 트랜잭션이므로 실패하면 차감분이 함께 롤백된다. T3는 주문 상태만 바꾼다.

**그 외**
- 같은 `productId`가 여러 번 들어오면 하나의 라인으로 합산한다
- 항목 중 하나라도 주문 불가면 주문 전체가 실패한다. 부분 주문은 만들지 않는다 (참고: Order-010)
- `AWAITING_PAYMENT` 이후 `PAID`로 가는 것도, `PAYMENT_FAILED`로 가는 것도 결제 요청이 트리거한다 (참고: Order-007, 07_payment.md)

**도메인 협력**
- `Order.draft(memberId, orderNumber, idempotencyKey)` — 주문 접수
- `Product.decreaseStock(quantity)` — 재고 차감 (참고: C.3)
- `Order.confirm(lines)` — 라인·총액 확정 및 `AWAITING_PAYMENT` 전이
- `Order.markOrderFailed()` — 확정 실패 처리

### UC-2. 유저의 주문 목록 조회

**목적**
로그인한 회원이 자신이 지금까지 한 주문들을 시간순으로 훑어본다.

**입력**

| 파라미터 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|
| `memberId` | MemberId | 필수 | 없음 | 조회 대상 회원 (X-MEMBER-ID 헤더에서 추출) |
| `page` | Int | 선택 | 0 | 페이지 번호 (0부터) |
| `size` | Int | 선택 | 20 | 페이지 크기 |

**출력**

주문 요약 목록과 페이징 메타.

주문 요약 정보:
- 주문번호, 주문 상태, 결제 수단, 총 결제 금액, 주문 시각
- 대표 상품명과 나머지 개수 (예: "무선 이어폰 외 2건")

페이징 메타:
- 전체 개수, 현재 페이지, 전체 페이지 수, 다음 페이지 존재 여부

**전제 조건**
- 사용자는 로그인 상태여야 함

**정렬 정책**
- 주문 시각 내림차순 (`orderedAt DESC`) — 최근 주문부터
- 정렬 결과 안정성을 위해 2차 정렬 키로 내부 `id` 사용. 이 값은 응답에 나가지 않는다 (참고: Order-011)

**필터/노출 정책**
- 본인의 주문만 조회된다. 다른 회원의 주문은 결과에 포함되지 않는다
- 상품의 현재 판매 상태와 브랜드 상태는 검사하지 않는다. 주문은 이미 일어난 사실의 기록이므로, 상품이 나중에 `HIDDEN`이 되어도 주문 내역에서 사라지지 않는다
- **`PENDING`과 `ORDER_FAILED`는 노출하지 않는다.** 사용자 입장에서 성립하지 못한 주문이며, 목록에 보이면 "주문했는데 왜 결제가 안 되지"라는 혼란만 만든다
- `AWAITING_PAYMENT`, `PAYMENT_FAILED`는 노출한다. 결제를 아직 안 한 주문과 실패한 주문을 사용자가 확인하고 이어서 결제할 수 있어야 한다

**처리 정책**
- 대표 상품명은 `OrderLine`에 스냅샷된 값을 쓴다. Product를 다시 조회하지 않는다 (참고: Order-001)
- 결제 수단은 Payment에서 읽는다. 주문 : 결제는 1:1이므로 조인 한 번으로 해결된다. 결제 요청 전인 주문은 Payment가 없어 이 값이 비어 있다 (참고: 07_payment.md Payment-001)

**도메인 협력**
> 단순 조회 유스케이스로, 도메인 객체에 호출되는 행위 없음.

### UC-3. 단일 주문 상세 조회

**목적**
회원이 특정 주문에 무엇이 담겼고 얼마를 어떻게 냈는지 확인한다.

**입력**

- `memberId` : MemberId — 조회 요청 회원 (X-MEMBER-ID 헤더에서 추출)
- `orderNumber` : String — 조회할 주문번호 (참고: Order-011)

**출력**

주문 상세 정보:
- 주문번호, 주문 상태, 총 결제 금액, 주문 시각, 결제 시각
- 주문 라인 목록 — 상품 ID, 주문 시점 상품명, 주문 시점 단가, 수량, 라인 금액
- 결제 정보 — 결제 수단, 결제 상태, 승인 시각, 실패 사유 (참고: 07_payment.md B.1)

**전제 조건**
- 사용자는 로그인 상태여야 함
- 해당 주문이 존재하고, 요청 회원의 주문이어야 함

**필터/노출 정책**
- 다른 회원의 주문을 조회하면 "찾을 수 없음"(404)으로 응답한다. 403이 아니라 404인 이유는 주문의 존재 여부 자체를 노출하지 않기 위해서다
- `PENDING`, `ORDER_FAILED` 주문도 "찾을 수 없음"(404)으로 응답한다. UC-2의 노출 정책과 일치시킨다
- 상품명과 단가는 주문 시점의 스냅샷 값이다. 현재 상품 정보와 다를 수 있다 (참고: Order-001)
- `status`가 `PAID`가 아니면 `paidAt`은 비어 있다
- 결제 요청 전인 주문은 결제 정보 전체가 비어 있다
- **PG 거래 식별자는 응답에 담지 않는다.** PG사와의 거래 식별자는 내부 대사(對事) 용도이며 사용자에게 의미가 없다

**도메인 협력**
> 단순 조회 유스케이스로, 도메인 객체에 호출되는 행위 없음.

## B. 구조

> 위 행위를 가능하게 하는 내부 구성. 애그리거트 루트와 내부 엔티티, 값 객체, 외부 관계로 이루어진다.

### B.1. Order : Entity, Aggregate Root

#### 속성

- `id` : Long — 내부 식별자
- `orderNumber` : String — 사용자에게 노출하는 주문번호 (참고: Order-011)
- `idempotencyKey` : String — 중복 요청 식별자 (참고: Order-004)
- `memberId` : Long — 주문한 회원 (ID 참조)
- `status` : OrderStatus — 주문 상태
- `totalAmount` : Money — 총 결제 금액. 확정 전에는 `Money.ZERO`
- `orderedAt` : ZonedDateTime — 주문 접수 시각
- `paidAt` : ZonedDateTime — 결제 완료 시각. `PAID`가 아니면 없음
- `lines` : List&lt;OrderLine&gt; — 주문 라인 목록 (애그리거트 내부, 참고: Order-008)

**불변식**

상태에 따라 성립하는 조건이 다르다. `PENDING`은 멱등키만 확정되고 상품도 재고도 아직 보지 않은 접수 기록이기 때문이다 (참고: Order-004).

| 조건 | 적용 상태 |
|---|---|
| `orderNumber`는 시스템 내에서 유일 | 전부 |
| `idempotencyKey`는 시스템 내에서 유일 | 전부 |
| `lines`는 비어 있고 `totalAmount`는 `Money.ZERO` | `PENDING`, `ORDER_FAILED` |
| `lines`는 1개 이상이고 `totalAmount`는 라인 합계와 같다 | `AWAITING_PAYMENT`, `PAID`, `PAYMENT_FAILED` |
| `lines` 안에서 `productId`는 중복되지 않는다 | 전부 |
| `paidAt`이 존재한다 | `PAID` |

#### 행위

- `draft(memberId, orderNumber, idempotencyKey)` : Order — 주문을 접수해 초안 상태로 만든다 (정적 팩토리). 상태는 `PENDING`, `totalAmount`는 `Money.ZERO`, `orderedAt`은 생성 시점
- `confirm(lines)` : void — 라인을 붙이고 총액을 계산한 뒤 `AWAITING_PAYMENT`로 전이한다. `PENDING`이 아니면 예외
- `markOrderFailed()` : void — 확정 실패 처리. 상태를 `ORDER_FAILED`로 바꾼다. `PENDING`이 아니면 예외
- `pay()` : void — 결제 완료 처리. 상태를 `PAID`로 바꾸고 `paidAt`을 기록한다. `AWAITING_PAYMENT`가 아니면 예외
- `markPaymentFailed()` : void — 결제 실패 처리. 상태를 `PAYMENT_FAILED`로 바꾼다. `AWAITING_PAYMENT`가 아니면 예외
- `isOwnedBy(memberId)` : Boolean — 해당 회원의 주문인지 반환한다. UC-3의 소유권 검사와 결제 요청의 소유권 검사에 쓰인다 (참고: 07_payment.md UC-1)
- `isPayable()` : Boolean — 결제를 받을 수 있는 상태인지 반환한다. `status.isPayable()`에 위임한다

> 주문 취소(`cancel()`)는 이번 feature 범위 밖이다. 취소 정책이 정해질 때 함께 추가한다 (참고: C.2).

### B.2. OrderLine : Entity (애그리거트 내부)

주문에 담긴 상품 한 종류를 표현한다. Order를 통해서만 접근한다 (참고: Order-008).

#### 속성

- `id` : Long — 식별자
- `productId` : Long — 주문한 상품 (ID 참조)
- `productName` : String — 주문 시점의 상품명 (스냅샷, 참고: Order-001)
- `unitPrice` : Money — 주문 시점의 단가 (스냅샷, 참고: Order-001)
- `quantity` : Int — 주문 수량

**불변식**
- `quantity`는 1 이상
- `unitPrice`는 0 이상 (`Money` 타입이 보장)

**파생 속성**
- `lineAmount` : Money — `unitPrice × quantity`

#### 행위

- `of(product, quantity)` : OrderLine — 상품과 수량으로 라인을 생성한다 (정적 팩토리). 상품명과 가격을 이 시점에 복사한다
- `lineAmount()` : Money — 라인 금액을 계산한다

### B.3. OrderStatus : Value Object

주문 상태를 나타내는 열거형.

#### 속성

- `PENDING` — 멱등키까지 확인해 접수됨. 상품 검증과 재고 확보는 아직 (참고: Order-004)
- `AWAITING_PAYMENT` — 재고 확보 완료. 결제를 기다리는 상태
- `ORDER_FAILED` — 접수 후 검증이나 재고 확보에 실패. 재고는 애초에 확보되지 않았다
- `PAID` — 결제 완료
- `PAYMENT_FAILED` — 결제 실패. **확보했던 재고가 복원된 상태** (참고: Order-007)

#### 행위

- `isPayable()` : Boolean — 결제를 받을 수 있는 상태인지 반환한다. `AWAITING_PAYMENT`만 `true`
- `isVisibleToUser()` : Boolean — 사용자 조회에 노출할 상태인지 반환한다. `PENDING`, `ORDER_FAILED`는 `false` (UC-2 / UC-3 노출 정책)

> `ORDER_FAILED`와 `PAYMENT_FAILED`는 **재고 상태가 다르다.** 전자는 확보에 실패한 것이라 되돌릴 게 없고, 후자는 확보했던 것을 되돌린 것이다. 같은 "실패"로 합치면 이 차이가 사라진다.
> `CANCELED`는 두지 않는다. 주문 취소가 이번 feature 범위 밖이라 진입 경로가 없기 때문이다 (참고: C.2).

---

### B.4. 다른 애그리거트와의 관계

- **Payment** → `Payment`가 `orderId`로 이 애그리거트를 참조함 (단방향, ID 참조). 1:1
    - Order는 Payment를 모른다. 결제 확정이 주문 상태를 바꾸는 방향(Payment → Order)만 존재한다 (참고: 07_payment.md Payment-001)
    - 결제 요청 전인 주문에는 대응하는 Payment가 없다
- **Product** ← `OrderLine.productId`로 참조 (단방향, ID 참조)
    - 주문 시 상품명·가격을 복사해 보관하므로, 이후 Product가 변경되거나 삭제되어도 주문 내용은 유지된다 (참고: Order-001)
    - 주문 확정 시 `Product`의 재고를 차감하고, 결제 실패 시 복원한다 (참고: Order-005, Order-007)
- **Member** ← `memberId`로 참조 (단방향, ID 참조)
    - 회원 도메인은 별도 컨텍스트로, ID로만 참조

## C. 설계 결정

> 확정된 결정과 보류된 결정을 함께 모은다. 보류된 항목이 결정되면 C.2 → C.1로 이동한다.

### C.1. 확정된 결정

> **왜 이런 선택을 했는지** 보존한다. 결정은 누적될 뿐 수정되지 않는다.

#### Order-001. 주문 시점의 상품명과 단가를 OrderLine에 스냅샷한다
- **일시**: 2026-08-25
- **결정**: `OrderLine`은 `productId`만 갖는 게 아니라 주문 확정 시점의 `productName`과 `unitPrice`를 복사해 보관한다. 주문 조회 시 Product를 다시 읽지 않는다.
- **이유**:
    - 주문은 "지금 이 상품"이 아니라 "그때 이 가격에 산 사실"의 기록이다. 상품 가격이 바뀌었다고 과거 영수증 금액이 따라 바뀌면 안 된다
    - 결제가 별도 요청이라 주문 확정과 결제 사이에 시간이 흐른다. 그 사이 가격이 바뀌어도 사용자가 주문서에서 본 금액으로 결제되어야 한다 (참고: Order-003)
    - 상품이 `HIDDEN`이 되거나 삭제돼도 주문 내역은 온전히 남아야 한다
- **영향**:
    - `Product.price` 변경이 기존 주문에 영향을 주지 않는다
    - 상품명이 오타로 수정되어도 과거 주문에는 옛 이름이 남는다 — 의도한 동작이다
    - `productId`는 "어떤 상품이었는지" 추적용으로만 남는다
- **관련 애그리거트**: Product
- **재검토 시점**: 상품 상세로 돌아가는 링크 등 최신 상품 정보가 필요해질 때 → 스냅샷은 유지하고 `productId`로 별도 조회하는 방식 우선 검토.

#### Order-002. 주문 총액은 서버가 재계산한다
- **일시**: 2026-08-25
- **결정**: 요청 바디에 금액 필드를 두지 않는다. 총액은 서버가 조회한 `Product.price`와 `quantity`로 계산한 값만 사용한다. 결제 금액도 이 값에서 가져오며, 결제 요청이나 PG 콜백이 전달하는 금액은 대조에만 쓴다.
- **이유**:
    - 클라이언트가 보낸 금액을 신뢰하면 가격 조작이 그대로 결제로 이어진다. 결제가 별도 요청이라 조작 지점이 하나 더 있다
    - 검증용으로 받아서 대조하는 방식도 고려했으나, 상품 목록을 본 시점과 주문 시점 사이에 가격이 정상적으로 바뀐 경우까지 실패로 만들게 된다
    - 금액을 아예 안 받으면 "받았는데 안 쓴다"는 애매한 상태가 생기지 않는다
- **영향**:
    - 사용자가 본 가격과 실제 주문 금액이 다를 수 있다. 응답의 `totalAmount`로 확인 가능하다
    - 결제 요청은 금액을 입력으로 받지 않고 `Order.totalAmount`를 그대로 쓴다 (참고: 07_payment.md UC-1)
    - PG 승인 금액이 주문 금액과 다르면 승인하지 않는다 (참고: 07_payment.md UC-2)
- **재검토 시점**: 가격 변동으로 인한 사용자 불만이 생길 때 → 클라이언트가 본 금액을 참고값으로 받아 불일치 시 경고하는 방식 검토.

#### Order-003. 주문과 결제를 별도 요청으로 분리한다
- **일시**: 2026-08-25
- **결정**: `POST /api/v1/orders`는 주문을 `AWAITING_PAYMENT`까지만 만든다. 결제는 클라이언트가 `POST /api/v1/payments`를 따로 호출해 진행한다. 주문 요청이 결제까지 오케스트레이션하지 않는다.
- **이유**:
    - **PG 결제는 외부 승인 왕복이 있어 주문 트랜잭션 안에 넣을 수 없다.** 사용자가 결제창에서 카드 정보를 입력하는 몇 분을 DB 트랜잭션이 기다릴 수 없다
    - 사용자가 주문서를 확정한 뒤 결제 수단을 고르는 것이 실제 구매 흐름이다. 두 단계를 한 요청으로 합치면 결제 수단을 주문서 작성 시점에 미리 정해야 한다
    - 결제 재시도 경로가 자연히 열린다. 결제만 다시 호출하면 되므로 주문을 새로 만들 필요가 없다
- **영향**:
    - `AWAITING_PAYMENT` 주문이 결제 요청 전까지 체류한다. 그 동안 재고가 묶인다 (참고: Order-005)
    - **결제하지 않은 주문을 정리하는 주체가 없다.** 사용자가 결제하기를 누르지 않으면 주문과 재고가 그대로 남는다 (참고: C.2)
    - 주문 응답에는 결제 정보가 없다. `status`는 `AWAITING_PAYMENT`다
    - 클라이언트가 두 번 호출해야 한다. 중간에 이탈할 지점이 하나 늘어난다
- **관련 결정**: Order-005(재고 차감 시점), Order-007(보상)
- **재검토 시점**: 결제 미이행 주문이 재고를 의미 있게 잠식할 때 → 만료 정리 배치 도입.

#### Order-004. 주문을 먼저 접수해 커밋하고, 확정은 다음 트랜잭션에서 한다
- **일시**: 2026-08-25
- **결정**: `Idempotency-Key` 헤더를 받아 `Order`를 `PENDING` 상태로 먼저 저장하고 커밋한다(T1). 상품 검증과 재고 확보는 그 다음 트랜잭션(T2)에서 수행하고 `AWAITING_PAYMENT`로 전이한다. 같은 키로 다시 요청이 오면 새 주문을 만들지 않고 기존 주문의 현재 상태를 돌려준다.
- **이유**:
    - **주문은 반드시 멱등해야 한다.** 더블 클릭, 네트워크 타임아웃 후 재전송, 클라이언트 자동 재시도로 같은 요청이 두 번 오는 일이 흔한데, 그때마다 주문이 두 건 생기면 재고가 두 번 빠지고 사용자는 두 번 결제하게 된다
    - 멱등성을 보장하려면 **판정 근거가 커밋되어 있어야 한다.** 검증과 재고 확보가 끝난 뒤에 저장하면, 그 사이에 도착한 두 번째 요청은 볼 것이 없어 그대로 통과한다. 접수 기록을 먼저 커밋해야 두 번째 요청이 그것을 발견한다
    - `Idempotency-Key`를 쓰는 이유는 자연 키(회원 + 장바구니 내용)로는 "같은 상품을 정말 두 번 사려는" 정상 요청과 구분되지 않기 때문이다. 결제 업계에서 널리 쓰는 방식이라 클라이언트 구현도 익숙하다
    - 키를 별도 테이블이 아니라 `Order`의 컬럼으로 둔 것은, 재요청 시 돌려줄 응답이 결국 주문 상태이기 때문이다. 응답을 따로 캐시할 필요가 없다
- **영향**:
    - `PENDING`은 **라인도 금액도 없는 주문**이다. B.1의 불변식이 상태에 따라 갈리게 된다
    - `idempotencyKey`에 UNIQUE 제약이 필요하다. 동시에 같은 키로 들어오면 제약 위반이 나며, 이는 중복 요청이라는 뜻이므로 기존 주문 조회로 전환한다
    - `Idempotency-Key` 헤더가 필수가 된다. 클라이언트가 매 주문 시도마다 새 UUID를 만들어야 한다
    - **T1 커밋 후 T2 시작 전에 프로세스가 죽으면 주문이 `PENDING`으로 영구 체류한다.** 재고는 안 빠졌으니 손해는 없지만, 정리하는 주체가 없다 (참고: C.2)
- **관련 결정**: Order-005(T2에서 재고 차감)
- **재검토 시점**: `PENDING` 잔재가 쌓여 조회를 방해할 때 → 만료 정리 배치 도입.

#### Order-005. 재고는 주문 확정 단계에서 차감한다
- **일시**: 2026-08-25
- **결정**: 재고 차감은 접수(T1)가 아니라 확정(T2)에서, 결제 요청보다는 앞서 수행한다. 재고를 잠시 잡아두는 "예약" 개념을 별도로 두지 않는다.
- **이유**:
    - **주문서를 확정한 사용자가 결제하기를 눌렀을 때 품절을 만나는 것이 최악의 경험이다.** 결제 수단까지 고른 뒤에 실패하면 그때까지의 조작이 전부 헛수고가 된다. 그래서 결제보다 앞이다
    - 접수(T1)에서 차감하지 않는 이유는, 그 시점에는 상품을 조회하지도 않았기 때문이다. 검증과 차감은 같은 트랜잭션에 있어야 중간 상태가 생기지 않는다
    - 예약 모델은 예약 만료 타임아웃, 만료 정리 배치, 예약 재고와 실재고의 이중 관리를 함께 데려온다. MVP에서 그 비용을 낼 만큼의 문제가 아직 없다
- **영향**:
    - **확정부터 결제 완료까지 재고가 묶인다.** 결제가 별도 요청이므로(Order-003) 이 구간의 길이는 전적으로 사용자 행동에 달려 있다. 결제하지 않으면 무한정이다 (참고: C.2)
    - T2가 실패하면 차감분이 트랜잭션 롤백으로 함께 되돌아간다. 별도 보상이 필요 없다 — 이것이 `ORDER_FAILED`와 `PAYMENT_FAILED`의 차이다
    - `Product.decreaseStock()`이 재고 부족 검사와 차감을 함께 수행한다. 검사와 차감이 분리되지 않아 그 사이의 간극은 없다
    - 동시 주문의 재고 경합은 비관적 락으로 막는다 (참고: Order-007)
- **관련 애그리거트**: Product (참고: 04_product.md)
- **재검토 시점**: 결제 미이행으로 묶이는 재고가 관측될 때 → 재고 예약 모델과 만료 배치를 함께 도입.

#### Order-006. 재고 경합은 비관적 락으로 막는다
- **일시**: 2026-08-26
- **결정**: 확정(T2)에서 상품을 읽을 때 `PESSIMISTIC_WRITE` 락을 걸어 읽는다. 여러 상품을 주문하면 `productId` 오름차순으로 정렬해 순서대로 잠근다.
- **이유**:
    - `Product.decreaseStock()`은 재고를 읽고 검사한 뒤 쓰는 read-modify-write다. 락이 없으면 두 요청이 같은 재고를 읽어 **둘 다 통과하고 재고가 음수로 간다**
    - 재고 검증이 도메인(`StockQuantity`)에 남는다. 조건부 UPDATE로 내리면 "재고가 충분한가"라는 규칙이 SQL의 WHERE 절로 새어 나가고, 엔티티는 자기 재고가 얼마인지 모르는 채 저장된다
    - 낙관적 락은 충돌 시 T2 전체를 되돌리고 재시도해야 한다. 재고는 경합이 잦은 필드라 재시도가 잦아지고, 그 재시도가 다시 경합을 만든다
    - MVP 트래픽에서 락 대기는 문제가 되지 않는다. 문제가 되는 시점에는 재고 예약 모델로 넘어갈 것이다 (참고: C.2)
- **영향**:
    - **여러 상품을 잠그므로 데드락이 가능하다.** 두 주문이 A·B를 서로 반대 순서로 잠그면 서로를 기다린다. `productId` 정렬로 잠금 순서를 고정해 막는다 — 이 정렬은 성능이 아니라 정합성을 위한 것이다
    - 인기 상품에 요청이 몰리면 그 상품을 담은 주문들이 직렬화된다. 락 구간은 T2 하나이므로 짧지만, 대기는 실재한다
    - 락은 T2 트랜잭션 경계 안에서만 유효하다. T1과 T2가 분리되어 있으므로(Order-004) 접수 시점에는 아무 것도 잠기지 않는다
    - 조회 전용 경로(UC-2/UC-3, 상품 목록)는 락을 걸지 않는다. 주문 확정 경로에서만 건다
- **관련 결정**: Order-005(T2에서 차감), Order-009(전체 실패이므로 일부만 잠긴 채 성공하는 경우가 없다)
- **관련 애그리거트**: Product (참고: 04_product.md)
- **재검토 시점**: 인기 상품의 락 대기가 응답 시간에 잡힐 때 → 재고 예약 모델 또는 조건부 UPDATE 재검토.

#### Order-007. 결제 실패 시 재고를 보상 복원한다
- **일시**: 2026-08-25
- **결정**: 결제가 실패하면 재고를 주문 수량만큼 복원하고, 주문을 `PAYMENT_FAILED`로 남긴다. 주문 레코드를 지우지 않는다. 결제 실패 사실의 확정은 Payment의 책임이고(참고: 07_payment.md B.1), 이 결정은 그것을 받아 재고와 주문을 되돌리는 쪽을 다룬다.
- **이유**:
    - Order-005가 재고를 확정 단계에서 차감하므로, 결제가 실패하면 되돌릴 주체가 필요하다. 결제가 별도 요청이라(Order-003) DB 롤백으로는 해결되지 않는다
    - 재고를 차감한 결정과 되돌리는 결정이 같은 곳에 있어야 둘이 어긋나지 않는다. 복원 수량은 항상 `OrderLine.quantity`이며 다른 근거를 두지 않는다
    - 실패한 주문이 기록으로 남아야 CS 문의와 디버깅에 쓰인다. 삭제하면 "주문이 안 됐다"는 문의에 답할 근거가 없다
- **영향**:
    - **보상이 실패하면 재고가 묶인 채 복구 수단이 없다.** 보상의 보상은 없다 (참고: C.2)
    - 포인트 결제는 결제 요청 안에서, PG 결제는 콜백 수신 시점에 같은 보상을 수행한다. 보상 로직은 한 곳에 두고 두 경로가 공유한다
    - `PAYMENT_FAILED` 주문은 재고가 복원된 상태이므로, 그대로 다시 결제할 수 없다. 재결제하려면 재고를 다시 확보해야 한다 (참고: C.2)
    - 만료 정리 배치를 두지 않는 이유는, 결제 결과를 받는 한 보상이 즉시 수행되기 때문이다. **결과 자체가 오지 않는 경우는 이 결정이 다루지 않는다** (참고: C.2)
- **관련 결정**: Order-003(요청 분리), Order-005(확정 단계에서 차감)
- **관련 애그리거트**: Product, Payment (참고: 07_payment.md UC-2)
- **재검토 시점**: 보상 실패가 실제로 관측될 때 → 재고 정합성 보정 배치를 먼저 도입하고 검토.

#### Order-008. OrderLine은 Order 애그리거트 내부다
- **일시**: 2026-08-25
- **결정**: `OrderLine`에 별도 Repository를 두지 않는다. 생성·조회·변경은 모두 `Order`를 통해서만 이루어지며, `OrderRepository.save(order)`가 라인까지 함께 영속화한다.
- **이유**:
    - 라인 단독으로는 의미가 없다. "주문 없는 주문 항목"은 존재할 수 없는 상태다
    - 총액 = 라인 합계라는 불변식을 지키려면 라인 변경이 반드시 Order를 거쳐야 한다. 라인 Repository를 열어두면 이 불변식을 우회할 경로가 생긴다
    - 라인 개수가 한 주문당 수십 개를 넘지 않아 함께 로딩해도 부담이 없다
- **영향**:
    - `OrderLine`은 애그리거트 루트가 아니다. ID 참조가 아니라 객체 참조로 연결된다. 결제가 별도 루트인 것과 대비된다 (참고: 07_payment.md Payment-001)
    - 라인이 붙는 시점은 `confirm()` 한 곳뿐이다. `PENDING` 주문에 라인을 끼워 넣을 경로가 없다 (참고: Order-004)
    - 주문 라인만 가로질러 조회하는 통계성 요구(예: 상품별 판매량)는 이 경로로 풀 수 없다. 조회 전용 모델이 필요하다 (참고: ProductLike-005의 판단과 동일한 성격)
- **재검토 시점**: 한 주문의 라인이 수백 개가 되거나, 라인 단위 조회가 주요 유스케이스가 될 때.

#### Order-009. 주문 가능 상품은 `ON_SALE` + 브랜드 `ACTIVE`만
- **일시**: 2026-08-25
- **결정**: 주문 확정(T2)은 `ON_SALE` 상태이고 소속 브랜드가 `ACTIVE`인 상품에만 허용한다. 그 외에는 "찾을 수 없음"(404)으로 응답한다.
- **이유**:
    - 사용자에게 노출되지 않는 상품은 주문할 경로 자체가 없다
    - 상품 조회(04_product.md UC-2)·좋아요 등록(ProductLike-007)과 같은 판단을 적용해, 같은 상품에 대해 조회는 404인데 주문은 성공하는 모순을 막는다
    - `ProductService.retrieve()`(판매 상태 검사) + `BrandService.retrieve()`(브랜드 상태 검사) 조합을 그대로 재사용할 수 있다. `ProductLikeProcessor`가 이미 쓰는 방식이라 별도 조회 메서드를 만들 필요가 없다
- **영향**:
    - 주문 목록·상세 조회(UC-2/UC-3)는 상품 상태를 검사하지 않는다. 이미 산 것을 못 보게 만들 이유가 없다
    - **검사는 T2에서만 한다. 결제 요청은 상품 상태를 다시 보지 않는다.** 확정한 뒤 상품이 `OFF_SALE`이 되어도 결제는 진행된다 — 재고를 이미 확보했고(Order-005), 사용자에게 책임을 지울 일이 아니기 때문이다
    - 장바구니가 도입되면 담아둔 상품이 `OFF_SALE`이 되는 경우를 별도로 다뤄야 한다
- **관련 애그리거트**: Product, Brand (참고: 03_brand.md Brand-001)
- **재검토 시점**: 예약 주문이나 재입고 알림 성격의 기능이 필요해질 때.

#### Order-010. 항목 중 하나라도 주문 불가면 주문 전체가 실패한다
- **일시**: 2026-08-25
- **결정**: 여러 상품을 주문할 때 일부만 품절이거나 노출 불가여도 부분 주문을 만들지 않는다. 주문 전체를 `ORDER_FAILED`로 실패시킨다.
- **이유**:
    - **장바구니가 도입되면 담는 단계에서 주문 가능 여부가 이미 확인되어야 한다.** 주문 시점의 부분 실패는 정상 흐름이 아니라 예외 상황이며, 예외 상황을 위해 부분 주문이라는 별도 개념을 만들 이유가 없다
    - 부분 주문은 사용자가 기대한 결제 금액과 실제 결제 금액을 어긋나게 한다. "5개 사려고 했는데 3개만 결제됨"은 금액 관련 분쟁으로 이어진다
    - 결제 요청이 `Order.totalAmount`를 그대로 쓰므로(Order-002), 부분 주문이 가능하면 결제할 금액이 무엇인지부터 모호해진다
- **영향**:
    - 인기 상품이 섞인 대량 주문은 재시도가 잦아질 수 있다. 재시도는 **새 `Idempotency-Key`로** 해야 한다 (참고: Order-004)
    - 실패 응답에 어떤 상품이 문제였는지 담을지는 에러 응답 스펙에서 별도로 정한다
- **재검토 시점**: 장바구니 도입 후에도 주문 시점 부분 실패가 잦게 관측될 때.

#### Order-011. 사용자 노출용 주문번호를 `id`와 별도로 채번한다
- **일시**: 2026-08-25
- **결정**: `Order`에 `orderNumber`를 두고 `yyyyMMdd-{8자리 랜덤 영숫자}` 형식으로 채번한다 (예: `20260825-A3F9K2QP`). **API가 주고받는 주문 식별자는 전부 이 값이며, `id`는 어디로도 나가지 않는다.**
- **이유**:
    - `id`를 그대로 노출하면 연속된 값이라 **총 주문량과 증가 속도가 그대로 드러난다**
    - **`id`가 나가는 지점이 하나라도 있으면 이 결정은 성립하지 않는다.** 응답 한 곳만 열려 있어도 클라이언트는 연속된 값을 관측한다. 그래서 URL 경로·요청 입력·응답 전부에서 걷어낸다
    - 날짜가 앞에 있어 CS 문의를 받았을 때 언제 주문인지 바로 가늠된다. 로그·PG 정산 내역과 대조하기도 쉽다
    - 랜덤 방식은 DB 시퀀스나 별도 채번 테이블 없이 애플리케이션에서 생성 즉시 확정된다. 일별 순번 방식은 동시 생성 시 채번 락이 필요하다
- **영향**:
    - `orderNumber`에 UNIQUE 제약이 필요하다. 충돌하면 재생성해 다시 저장한다
    - 접수(T1)에서 채번한다. 이후 모든 단계가 이 값으로 주문을 가리킨다 (참고: Order-004)
    - 주문 상세 조회(`/api/v1/orders/{orderNumber}`), 결제 요청(참고: 07_payment.md UC-1), PG 콜백(참고: 07_payment.md UC-2)이 모두 이 값을 쓴다. 사용자가 CS에 불러주는 값과 URL에 보이는 값이 같다
    - `id`는 내부 FK(`Payment.orderId`)와 목록 조회의 2차 정렬 키로만 남는다
    - `orderNumber`가 조회 키가 되므로 UNIQUE 인덱스가 제약과 조회 인덱스를 겸한다. PK 조회 대비 비용 차이는 사실상 없다
- **재검토 시점**: 일 주문량이 늘어 충돌 재시도가 모니터링에 잡힐 때 → 자릿수 확대 또는 ULID 검토.

### C.2. 보류된 결정

> 아직 결정되지 않았거나 **앞으로 다룰 항목**을 모은다. 결정되면 C.1로 이동한다.

- [ ] **결제하지 않은 `AWAITING_PAYMENT` 주문의 정리** — 주문만 확정하고 결제하지 않으면 재고가 무한정 묶인다. 결제가 별도 요청이라 이 구간의 길이를 서버가 통제할 수 없다. 만료 타임아웃 + 정리 배치가 필요하다 (관련: Order-003, Order-005)
- [ ] **`PENDING`으로 남은 주문의 정리** — T1 커밋 후 T2 전에 프로세스가 죽은 경우다. 재고는 안 빠졌지만 잔재가 쌓인다 (관련: Order-004)
- [ ] **주문 취소와 환불** — 이번 feature 범위 밖. `CANCELED` 상태 추가, 포인트 복원, PG 승인 취소가 여기 딸린다 (관련: 07_payment.md C.2)
- [ ] **`PAYMENT_FAILED` 주문의 재결제** — 보상으로 재고가 이미 복원되어(Order-007) 재고 재확보가 선행되어야 한다. `Payment.orderId` UNIQUE 제약도 함께 재검토가 필요하다 (관련: 07_payment.md Payment-001)
- [ ] `Idempotency-Key`의 유효 기간과 정리 정책 — 무기한 보관하면 주문 테이블에 계속 쌓인다 (관련: Order-004)
- [ ] 보상이 실패했을 때의 재고 복구 수단 (관련: Order-007)
- [ ] 재고 예약과 예약 만료 타임아웃 (관련: Order-005)
- [ ] 장바구니 도입 (현재는 요청 바디에 항목을 직접 담는 방식 — 관련: Order-010)
- [ ] 쿠폰·할인 금액 반영
- [ ] 배송지와 배송 상태
- [ ] 도메인 이벤트 도입 (`OrderConfirmed`, `OrderPaid`)

### C.3. 선행으로 필요한 코드 변경

> 주문을 구현하기 전에 기존 코드에 없는 것들. 문서만 보고는 알 수 없어 남긴다.

| 대상 | 필요한 것 |
|---|---|
| `domain/shared/Money.java` | `multiply(int)` 없음. `lineAmount = unitPrice × quantity` 계산에 필요 |
| `domain/product/Product.java` | 재고 차감·복원 행위 없음. `decreaseStock(quantity)`, `increaseStock(quantity)` 필요 |
| `domain/product/StockQuantity.java` | `isSoldOut()`만 있음. `isEnough(quantity)` / `subtract(quantity)` / `add(quantity)` 필요 |
| `domain/order` (신설) | 주문번호 채번 유틸 (Order-011 형식) |
| `interfaces/api/order` (신설) | `Idempotency-Key` 헤더 추출. `X-MEMBER-ID`와 같은 방식 |
