## 3. 공백이 생긴 이유

공백은 실수가 아니라 **개발자 테스트의 구조에서 자연스럽게 생긴다.**

1. **테스트 더블이 경계를 가린다.** E2E가 `PaymentGateway`를 Mock으로 바꾼 덕에 빠르고 결정적이지만, 그 대가로 어댑터·재시도·서킷·실제 HTTP가 결제 흐름과 함께 도는 경로는 한 번도 실행되지 않는다. 각 부품은 따로 검증되었지만 **조립된 시스템**은 검증되지 않았다.
2. **명세를 기준으로 테스트를 쓰면 명세의 빈틈도 그대로 물려받는다.** 콜백 발신자 검증, 동시 콜백, PG 재전송 정책은 명세에 없거나 "안전하다"고 적혀 있어 테스트 대상으로 떠오르지 않았다.
3. **동시성 테스트가 알려진 경로에만 있다.** 같은 주문 동시 결제는 UNIQUE가 막는다는 설계 의도를 확인하는 테스트다. 설계가 막지 않는 경로(다른 주문, 동시 콜백)는 테스트가 없다.
4. **블랙박스로 관측할 수단이 없다.** 주문 상세 조회가 없어 테스트가 결과를 DB로 확인한다. 그러다 보니 "사용자가 결과를 볼 수 없다"는 문제 자체가 테스트에서 드러나지 않았다.

## 4. 이번 스프린트가 채울 공백 (우선순위)

| 순위 | 공백 | 레벨 | 위치 | 질의·발견 |
|---|---|---|---|---|
| 1 | 다른 주문 동시 포인트 결제 | 통합 | 앱 저장소 JUnit | Q-A3 / F-6 |
| 2 | 위조 콜백 | API | Playwright | Q-B5 / F-1 |
| 3 | 동시 중복·상반 콜백 | 통합 | 앱 저장소 JUnit | Q-B2, Q-B3 / F-2 |
| 4 | 요청 → PG → 콜백 → 종결 전체 왕복 | E2E | Playwright + compose | Q-B1, Q-A5 |
| 5 | 실제 HTTP로 재시도·서킷까지 조립된 경로 | 시스템 | Playwright + compose (PG 대역) | Q-C1, Q-C2 |
| 6 | 콜백 처리 실패 후 결제 상태 (재전송 없음) | 시스템 | Playwright + compose | Q-B4 / F-3 |
| 7 | 로그·응답의 카드번호 평문 | 시스템 | Playwright + 로그 검사 | Q-D1 |

## 5. 커버리지 측정 (로컬에서 실행)

이 분석은 테스트 목록과 코드를 대조한 정적 분석이다. 커버리지 수치는 Docker가 있는 로컬에서 아래로 확인하고 이 절에 채운다.

> 커버리지가 높게 나와도 위 공백은 그대로다. 공백의 대부분은 **실행되지 않은 코드**가 아니라 **실행된 적 없는 조합**(동시 실행, 조립된 경로, 공격 입력)이기 때문이다. 이것이 이 분석을 커버리지 숫자보다 먼저 한 이유다.
