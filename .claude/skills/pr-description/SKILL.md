# PR 설명 문서 작성

**기능 하나가 끝났을 때 한 번 쓴다.** `docs/pr/NN_기능.md` 에 만든다.

`featureN` 이 아니라 **`pr_docs` 브랜치에 커밋한다.** PR 설명을 그 PR 의 diff 안에 넣으면
리뷰 대상이 되어버린다.

## 무엇을 쓰는가

**한 것 / 고민한 것 / 어떻게 정했는지.** 이 셋이 아니면 쓰지 않는다.

리뷰어는 **최종 상태를 본다.** 거기까지 어떻게 왔는지는 리뷰어가 할 수 있는 일이 없다.

## 절 구성

| 절 | 담는 것 |
|---|---|
| `## 배경` | **한 줄.** 무엇이 문제였고 무엇을 하려는지 |
| `## 변경 사항` | 무엇이 어떻게 달라졌는지. 3~5줄 |
| `## 기술적 판단` | **가장 중요한 절.** 갈림길과 고른 이유 |
| `## 테스트` | 이 PR 에서 **새로 확인하게 된 것**만 |

`## 감수한 것` 은 해결하지 않고 넘어간 한계가 있을 때만 둔다.

**도메인 설계 결정이 여러 개라 `## 기술적 판단` 이 비대해지면 `## 주요 설계 사항` 으로 떼어낸다.**
기술적 판단에는 작업 방식·형식에 대한 판단이 남고, 설계 결정은 새 절로 간다. 기본은 한 절이다 —
판단이 두세 개면 쪼개지 않는다.

**이번 범위가 아닌 것**은 배경 아래 인용으로 먼저 밝힌다. 명세에는 있는데 코드에 없으면
리뷰어가 빠뜨린 줄 안다.

### 변경 사항 — 코드를 모르는 사람이 한눈에 보게

**클래스명·애노테이션 나열이 아니라 "무엇이 어떻게 달라졌나" 를 쓴다.**

```markdown
❌ RegisterRequest 의 loginId/email/password 에 @NotBlank 추가

✅ | 요청 | 값 | 전 | 후 |
   |---|---|---|---|
   | 회원가입 | 이메일 없음 | **500** | 400 |
   | 회원가입 | 성별에 "X" | **500** | 400 + 사용 가능한 값 안내 |
```

애노테이션 이름은 diff 를 열면 보인다. 리뷰어가 알고 싶은 것은 **결과가 어떻게 바뀌는가** 다.

### 기술적 판단 — 무엇을 버렸는지가 있어야 판단이다

**판별 기준은 하나다. 다른 선택지가 실재했는가, 그걸 왜 버렸는가.**
저울질하지 않았다면 판단이 아니라 변경 사항이다. `@Enumerated` 를 빠뜨려 ORDINAL 로
저장되던 것을 고친 것이 그런 자리다 — 다른 선택지가 없었다.

```markdown
❌ 유니크 제약으로 중복을 막는다. DB 가 원자적으로 보장하고 락 경합도 없다.
   → 무엇을 했는지만 있다. 무엇을 버렸는지가 없다

✅ **무엇으로 막나 — 락이 아니라 DB 유니크 제약.** 락은 이미 있는 행을 고칠 때 쓰는 것인데,
   가입은 아직 없는 행을 만드는 상황이라 잠글 대상이 없다. `FOR UPDATE` 로 없는 행을 잠그면
   갭 락으로 번져 데드락이 된다.
   → 버린 것(락)과 버린 이유가 함께 있다
```

같은 결정을 두 가지로 쓴 것이다. 차이는 형식이 아니라 **버린 선택지가 있느냐** 에 있다.

- 제목을 **"갈림길 — 고른 것"** 으로 적으면 대비가 한 줄에 드러난다
- 여러 판단이 한 주제의 다른 각도라면 앞에 그 주제를 한 줄로 밝힌다

### 항목 형식 — 번호 헤딩 + 한 줄 불릿

**판단 하나가 `### N. 제목` 이고, 그 아래 불릿이 1~3개다.** 결정 번호가 있으면 제목 끝 괄호에 담는다.
굵은 글씨로 시작하는 문단은 쓰지 않는다 — 항목이 셋을 넘으면 어디서 끊기는지 보이지 않는다.

```markdown
### 1. 좋아요 수는 `Product.likeCount` 캐시 컬럼에 둡니다 (Product-003)
- `likeDesc` 정렬이 `ORDER BY` 에 쓸 값이라 조회마다 `COUNT` 를 돌릴 수 없습니다
- 대가로 좋아요 추가·삭제가 같은 트랜잭션에서 `Product` 를 함께 건드립니다
```

**불릿 하나는 한 줄이다.** 두 줄을 넘으면 두 개로 쪼갠다. 묶음의 주제를 밝히는 한 줄은
절 머리에 인용(`>`)으로 둔다.

**근거가 한 줄로 서면 불릿 하나로 끝낸다.** 개수를 채우려 대가나 배경을 덧붙이지 않는다.
제목이 "무엇을 했나" 를 이미 말하므로 불릿에는 **이유만** 남으면 된다.

```markdown
### 2. 숨긴 상품을 쿼리로 거르지 않고, DB에서 조회 후 도메인 로직에서 판단합니다
- 노출 규칙이 SQL 로 흩어지는 것을 방지하기 위해 `findById` 로 조회하고
  규칙을 도메인(`isVisibleToUser()`)에 둡니다
```

### 근거를 지우고 결론만 압축하지 않는다

짧게 쓰라는 것은 **근거를 빼라는 뜻이 아니다.** 근거가 사라진 자리에는 뜻을 알 수 없는 형용구만
남고, 리뷰어는 되물어야 한다.

```markdown
❌ 읽기 전용이고 도메인 규칙이 작동하지 않는 자리라 조회 전용 모델을 뒀습니다
   → "도메인 규칙이 작동하지 않는다" 가 무슨 뜻인지, 그래서 왜 되는지가 없다

✅ 상태를 바꾸지 않고 엔티티의 행위도 부르지 않아, 애그리거트를 거쳐야 지킬 불변식이 없습니다
   → 조인 결과를 그대로 받는 조회 전용 모델로 뒀습니다
```

**근거를 앞에, 결론을 화살표 뒤에** 두면 한 줄로 줄여도 왜 그런지가 남는다.

## 쓰지 않는 것

### 1. 코드가 이미 말하는 것

```markdown
❌ 회원 식별은 `X-MEMBER-ID` 헤더. 요청 바디는 `{ "orderNumber": "...", "method": "POINT" }` 뿐이다.
```

헤더는 모든 엔드포인트가 쓰는 기존 컨벤션이고, 바디는 Request record 한눈에 보인다.
**바디에서 말할 값어치가 있는 것**(금액을 받지 않는다)은 결정 불릿이 이미 말한다.

레이어별 테스트 애노테이션 표, 응답 필드 나열, 패키지 구조도 같은 자리다.

### 2. 작업 과정 서술

```markdown
❌ 명세 초안은 "승인 / 실패 처리" 둘이었는데 그대로는 구현되지 않았다.
❌ 처음엔 `RuntimeException` 을 잡아 보상을 불렀다.
```

내가 어떤 경로로 결론에 왔는지는 diff 에 없다. **결론과 이유만** 쓴다.
단, **리팩토링 PR 은 예외다** — 이전 상태가 곧 리뷰 대상이다.

### 3. 절차와 방식

TFD 를 어떤 순서로 돌았는지, 커밋마다 스켈레톤이 몇 개였는지, Testcontainers 를 쓴다는 것,
파생 쿼리라 인프라 테스트를 안 만들었다는 것. 전부 뺀다.

뮤테이션 검증도 절차와 "잡아낸 목록"은 쓰지 않는다 — `test-effectiveness` 4절과 같다.
**고친 결과만** 쓴다.

### 4. 값을 못 하는 표

1~2 행짜리 표는 문장으로 쓴다. 표는 **여러 항목을 나란히 비교할 때**만 쓴다.

**셀 하나가 두 줄을 넘으면 문단으로 바꾼다.** 근거를 길게 써야 하는 판단은 표에 안 맞는다.
제목에 대비를 담고 본문에서 풀어 쓰는 편이 읽힌다.

## 테스트 절

**이 PR 이 새로 확인하게 된 것만 쓴다.**

- ❌ **전체 통과 개수** — 리포의 현재 상태이지 이 PR 이 한 일이 아니다
- ❌ **"커밋마다 테스트가 통과한다"** — 당연한 절차라 적을 값어치가 없다
- ✅ 새로 붙인 테스트가 **무엇을 잡는지**, 왜 그 층에 뒀는지
- ✅ **결함을 심어 실제로 빨간불이 되는지 확인했다면** 그것

**무엇을 했는지를 앞에, 이유를 뒤에** 붙여 한두 줄로 끝낸다.

```markdown
- **컨트롤러 슬라이스 테스트에서 성공 케이스와 예외 매핑을 걷어냈다.** 목이 답을 주는 테스트라
  회귀를 잡지 못하고, `재고 부족 → 409` 같은 이름은 실제로는 매핑만 검증해 이름이 거짓이 된다
```

테스트를 새로 나눈 기준(어느 테스트가 무엇을 맡는지)도 한 줄로 적는다. 개수가 적은 이유를
리뷰어가 묻게 되는 자리다.

## 감수한 것은 적는다

해결하지 않고 넘어간 한계는 **숨기지 않는다.** 어디에 남겨뒀는지(명세의 보류 항목 등)까지 적는다.
리뷰어가 알아야 판단할 수 있고, 모르면 지적으로 돌아온다.

## 분량

**80줄 안팎.** 넘으면 위의 "쓰지 않는 것" 중 하나가 들어간 것이다.
