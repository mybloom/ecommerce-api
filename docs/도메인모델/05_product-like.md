# ProductLike 애그리거트

> **범위**: 큐레이션 오픈마켓 MVP — 사용자 관점

---

## A. 행위

> **책임**: 어떤 사용자가 어떤 상품에 표현한 좋아요를 기록한다. 상품 정렬과 사용자별 좋아요 표시 조회의 근거가 된다.

### API 엔드포인트

| METHOD | URI | 설명 | 대응 UC |
|---|---|---|---|
| POST | `/api/v1/like/products/{productId}` | 상품 좋아요 등록 | UC-1 |
| DELETE | `/api/v1/like/products/{productId}` | 상품 좋아요 취소 | UC-2 |
| GET | `/api/v1/like/products` | 내가 좋아요 한 상품 목록 조회 | UC-3 |

### UC-1. 상품 좋아요 누르기

**목적**  
로그인한 사용자가 특정 상품에 좋아요를 표현한다.

**입력**

- `memberId` : MemberId — 좋아요를 누르는 회원 (인증 컨텍스트에서 추출)
- `productId` : ProductId — 좋아요 대상 상품

**출력**

- 좋아요 적용 결과 (성공 여부, 갱신된 좋아요 수)

**응답 바디**

| 필드 | 타입 | 설명 |
|---|---|---|
| `memberId` | Long | 좋아요를 누른 회원 |
| `productId` | Long | 좋아요 대상 상품 |
| `isDuplicatedRequest` | boolean | 이미 좋아요한 상태였는지. `true`면 좋아요 수 변화 없음 |

> 위 **출력**의 "갱신된 좋아요 수"는 응답 바디에 포함하지 않는다 (2026-08-24 확정).
> 카운트가 필요한 클라이언트는 상품 조회로 다시 받는다.

**전제 조건**
- 사용자는 로그인 상태여야 함
- 대상 Product는 존재해야 함
- 대상 Product는 `ON_SALE` 상태여야 함 (참고: ProductLike-007)
    - `OFF_SALE`, `HIDDEN` 상품이나 비활성 브랜드의 상품은 "찾을 수 없음"(404) 응답

**처리 정책**
- (memberId, productId) 조합이 이미 존재하면 멱등 처리 (성공 응답, 카운트 증가 없음)
- ProductLike 생성과 Product 카운트 증가는 동일 트랜잭션 (참고: Product-003)

**도메인 협력**
- ProductLike 생성 (`ProductLike.like(memberId, productId)`)
- Product 좋아요 수 증가 (`Product.increaseLikeCount()`)

---

### UC-2. 상품 좋아요 취소

**목적**  
로그인한 사용자가 이전에 누른 좋아요를 취소한다.

**입력**

- `memberId` : MemberId — 좋아요를 취소하는 회원 (인증 컨텍스트에서 추출)
- `productId` : ProductId — 좋아요 취소 대상 상품

**출력**

- 좋아요 취소 결과 (성공 여부)

**응답 바디** (참고: ProductLike-008)

| 필드 | 타입 | 설명 |
|---|---|---|
| `memberId` | Long | 좋아요를 취소한 회원 |
| `productId` | Long | 좋아요 취소 대상 상품 |
| `isDuplicatedRequest` | boolean | 이미 좋아요가 없던 상태였는지. `true`면 좋아요 수 변화 없음 |

> UC-1과 동일한 형식이며 "갱신된 좋아요 수"는 포함하지 않는다 (참고: ProductLike-008).

**전제 조건**
- 사용자는 로그인 상태여야 함
- **상품의 판매 상태와 브랜드 상태는 검사하지 않는다** (참고: ProductLike-007)

**처리 정책**
- (memberId, productId) 조합이 존재하지 않으면 멱등 처리 (성공 응답, 카운트 감소 없음)
- ProductLike 삭제와 Product 카운트 감소는 동일 트랜잭션 (참고: Product-003)

**도메인 협력**
- ProductLike 삭제 — Repository가 수행한다 (참고: ProductLike-009)
- Product 좋아요 수 감소 (`Product.decreaseLikeCount()`)

### UC-3. 내가 좋아요한 상품 목록 조회

**목적**  
로그인한 사용자가 자신이 좋아요를 누른 상품들을 모아서 본다. 

**입력**

- `memberId` : MemberId — 조회 대상 회원 (인증 컨텍스트에서 추출)
- `page` : Int — 페이지 번호 (0부터, 기본 0)
- `size` : Int — 페이지 크기 (기본 20)

**출력**

상품 요약 목록과 페이징 메타.

상품 요약 정보 (Product UC-1과 동일):
- 상품 ID, 상품명, 대표 이미지
- 브랜드 ID, 브랜드명
- 가격, 좋아요 수, 품절 여부

추가 정보:
- 좋아요를 누른 시각 (`likedAt`)

페이징 메타:
- 전체 개수, 현재 페이지, 전체 페이지 수, 다음 페이지 존재 여부

**전제 조건**
- 사용자는 로그인 상태여야 함

**정렬 정책**
- 좋아요를 누른 시각의 내림차순 (`likedAt DESC`) — 최근에 찜한 것부터
- 정렬 결과 안정성을 위해 2차 정렬 키로 `productLikeId` 사용

**필터/노출 정책** (참고: ProductLike-003)
- 노출 대상:
    - `ON_SALE` (판매 중) 상품
    - `OFF_SALE` (판매 중지) 상품
    - 품절 상품 (품절 뱃지 표시)
- 비노출 대상:
    - `HIDDEN` (숨김) 상품
    - 비활성 브랜드의 상품 (참고: Brand-001)
    - 시스템에서 삭제된 상품

**처리 정책**
**처리 정책**
- ProductLike, Product, Brand를 단일 쿼리로 조인하여 상품 요약 구성
- 필터링은 조회 시점에 WHERE 절에서 함께 수행 (페이징 정확성 보장)
- 애그리거트 경계 관점에서 도메인 모델을 거치지 않고 조회 전용 모델로 직접 처리

**도메인 협력**
> 단순 조회 유스케이스로, 도메인 객체에 호출되는 행위 없음.
> 구체적인 조회 흐름은 시퀀스 다이어그램으로 별도 정리.

## B. 구조

> 위 행위를 가능하게 하는 내부 구성. 애그리거트 루트와 외부 관계로 이루어진다.

### B.1. ProductLike : Entity, Aggregate Root

#### 속성

- `id` : Long — 식별자
- `memberId` : Long — 좋아요를 누른 회원 (ID 참조)
- `productId` : Long — 좋아요 대상 상품 (ID 참조)
- `likedAt` : ZonedDateTime — 좋아요를 누른 시각

**불변식**
- `(memberId, productId)` 조합은 시스템 내에서 유일

#### 행위

- `like(memberId, productId)` : ProductLike — 새 좋아요 인스턴스를 생성한다 (정적 팩토리). `likedAt`은 생성 시점으로 설정
> 취소 시 제거는 엔티티가 아니라 Repository가 수행한다. 엔티티에 `unlike()`를 두지 않는다 (참고: ProductLike-009)

---

### B.2. 다른 애그리거트와의 관계

- **Product** ← `productId`로 참조 (단방향, ID 참조)
    - ProductLike 추가/삭제 시 `Product.likeCount` 동기 업데이트 (참고: Product-003)
    - Product가 삭제될 경우 해당 ProductLike도 함께 정리됨 (종속적 생명주기)
- **Member** ← `memberId`로 참조 (단방향, ID 참조)
    - 회원 도메인은 별도 컨텍스트로, ID로만 참조

## C. 설계 결정

> 확정된 결정과 보류된 결정을 함께 모은다. 보류된 항목이 결정되면 C.2 → C.1로 이동한다.

### C.1. 확정된 결정

> **왜 이런 선택을 했는지** 보존한다. 결정은 누적될 뿐 수정되지 않는다.

#### ProductLike-001. 중복 좋아요와 부재 취소는 멱등 처리
- **일시**: 2026-05-07
- **결정**: 이미 좋아요를 누른 상태에서 다시 누르거나, 누르지 않은 상태에서 취소 요청을 받으면 에러 없이 멱등하게 처리한다.
- **이유**:
    - 네트워크 재전송, 더블 클릭 등 의도치 않은 중복 요청이 흔함
    - 클라이언트 상태와 서버 상태의 미세한 불일치로 인한 사용자 불편 회피
    - 좋아요라는 행위 자체가 "특정 상태 도달"이 목표이지 "특정 변화"가 목표가 아님
- **영향**:
    - 응답은 항상 성공 (현재 좋아요 상태 + 갱신된 카운트 반환)
    - 카운트는 실제 상태가 변할 때만 증감
- **재검토 시점**: 좋아요 행위에 대한 정확한 이력 추적이 필요해질 때.

#### ProductLike-002. 단일 식별자 + 복합 유니크 제약 사용
- **일시**: 2026-05-07
- **결정**: ProductLike의 식별자는 단일 `id`(Long)를 사용하고, `(memberId, productId)`에는 UNIQUE 제약을 부여한다.
- **이유**:
    - 단일 ID로 참조/관리가 단순해짐 (URL 경로, 로그 추적 등)
    - 향후 좋아요 이력 보존(soft delete 등) 같은 확장에 유리
    - 복합키만 쓰면 조회/수정 시 매번 두 컬럼을 다뤄야 해 번거로움
- **영향**:
    - DB 레벨에서 `(memberId, productId)` UNIQUE 인덱스 필요
    - 동시 요청으로 인한 중복 생성은 UNIQUE 제약으로 차단됨
- **재검토 시점**: 식별자 정책 전반이 바뀔 때.

#### ProductLike-003. 좋아요한 상품 목록의 노출 정책
- **일시**: 2026-05-07
- **결정**: 사용자가 좋아요한 상품 목록 조회(UC-3) 시, 다음 정책에 따라 노출한다.
    - **노출**: `ON_SALE`(판매 중), `OFF_SALE`(판매 중지), 품절 상품
    - **비노출**: `HIDDEN`(숨김), 비활성 브랜드의 상품, 시스템에서 삭제된 상품
- **이유**:
    - 위시리스트는 "내가 관심을 표현한 것들"의 기록 — 사용자 입장에서 일시적으로 판매 중지된 상품이 사라지면 혼란
    - 품절/판매 중지된 상품도 재입고/재판매 시 사용자가 알아챌 기회 제공
    - 단, `HIDDEN`과 비활성 브랜드는 운영상 강한 차단 의지가 있는 상태로, 일관되게 비노출 (Brand-001 결정과 정합성)
- **영향**:
    - UC-3에서는 Product UC-1과 다른 별도 필터 조건 적용
    - "재입고/재판매 알림" 같은 후속 기능과 연결 가능
- **관련 애그리거트**: Product, Brand

#### ProductLike-004. 좋아요 취소는 Hard Delete로 처리
- **일시**: 2026-05-07
- **결정**: 좋아요 취소 시 ProductLike 인스턴스를 물리적으로 삭제한다 (Soft Delete 사용 안 함).
- **이유**:
    - 좋아요는 현재 상태를 표현하는 행위로, 이력 보존 가치가 낮음
    - 좋아요/취소 토글이 빈번한 행위라 Soft Delete 시 데이터 누적 부담이 큼
    - 모든 쿼리에 `deletedAt IS NULL` 조건이 추가되는 부담 회피
    - `(memberId, productId)` UNIQUE 제약이 단순해짐
- **영향**:
    - 한 번 취소된 좋아요는 복구 불가
    - 좋아요 행위에 대한 이력/분석이 필요하면 별도 이벤트 로그 도입 필요
- **재검토 시점**: 좋아요 행위에 대한 정확한 이력 추적이 필요해질 때 (별도 이벤트 로그 도입을 우선 검토하고, 그래도 부족할 때 Soft Delete 검토).

#### ProductLike-005. UC-3 조회는 조회 전용 모델로 단일 쿼리 처리
- **일시**: 2026-05-07
- **결정**: 좋아요한 상품 목록 조회(UC-3) 시, ProductLike + Product + Brand를 단일 쿼리로 조인하여 처리한다. 각 애그리거트의 Repository를 거쳐 메모리에서 조합하지 않는다.
- **이유**:
    - 페이징 정확성 보장 — 필터링이 조회 시점에 함께 일어남
    - DB 왕복 1회로 성능 유리 (위시리스트는 자주 호출되는 화면)
    - 위시리스트 조회는 읽기 전용이며 도메인 규칙이 작동하지 않음
- **영향**:
    - 애그리거트 경계를 우회하는 조회 전용 모델 도입 (예: `WishlistView`, `MemberLikedProductQuery`)
    - 도메인 변경(예: 가격 변경)이 즉시 반영됨 (캐시 적용 시 별도 무효화 전략 필요)
    - DDD 일반 원칙(애그리거트 경계 존중)에 대한 의도적 예외임을 명시
- **재검토 시점**:
    - 위시리스트가 자주 호출되어 캐시 도입 시 — 캐시 키 설계와 함께 재검토
    - CQRS의 Read Side로 별도 모델 분리 시점

#### ProductLike-006. 동시 요청의 UNIQUE 제약 위반은 멱등 성공으로 변환
- **일시**: 2026-08-24
- **결정**: 같은 `(memberId, productId)`로 동시 요청이 들어와 DB UNIQUE 제약 위반이 발생하면, 예외를 잡아 `isDuplicatedRequest = true`인 성공 응답으로 변환한다. `Product.likeCount`는 증가시키지 않는다.
- **이유**:
    - 애플리케이션의 중복 검사(존재 확인 후 저장)는 검사와 저장 사이에 다른 요청이 끼어들 수 있어 동시 상황에서 뚫림
    - ProductLike-001이 멱등 처리의 근거로 든 "더블 클릭"이 바로 이 동시 요청 상황이므로, 그 결정을 동시성 구간까지 일관되게 적용
    - 락이나 요청 직렬화 없이 DB 제약만으로 정합성을 지키면서 사용자 경험을 유지할 수 있음
- **영향**:
    - 좋아요 등록 경로에서 UNIQUE 위반 예외를 포착하는 처리 필요
    - 클라이언트는 동시 요청 여부와 무관하게 항상 동일한 형태의 성공 응답을 받음
- **관련 결정**: ProductLike-001(멱등 처리), ProductLike-002(UNIQUE 제약)
- **재검토 시점**: 좋아요 요청량이 늘어 예외 발생이 모니터링에 유의미하게 잡힐 때 → 사전 락 또는 upsert 방식 검토.

#### ProductLike-007. 좋아요는 `ON_SALE` 상품에만 허용
- **일시**: 2026-08-24
- **결정**: 좋아요 등록(UC-1)은 `ON_SALE` 상태이고 소속 브랜드가 `ACTIVE`인 상품에만 허용한다. 그 외에는 "찾을 수 없음"(404)으로 응답한다.
- **이유**:
    - 사용자에게 노출되지 않는 상품은 좋아요를 누를 경로 자체가 없다
    - 기존 `ProductService.retrieve()`를 그대로 재사용할 수 있어 상태 검사를 우회하는 별도 조회 메서드를 만들 필요가 없다
    - 노출 정책을 상품 조회(04_product.md UC-2)와 일치시켜, 같은 상품에 대해 조회는 404인데 좋아요는 성공하는 모순을 막는다
- **영향**:
    - UC-1 전제 조건에 상태 제약 추가
    - **좋아요 취소(UC-2)는 상태와 무관하게 동작해야 한다.** 이미 찜한 상품이 나중에 `OFF_SALE`로 바뀌어도 취소는 가능해야 하기 때문이다
    - 좋아요한 상품 목록(UC-3)의 노출 정책과는 별개다. 목록은 `OFF_SALE`도 노출한다 (참고: ProductLike-003)
- **재검토 시점**: 판매 중지 상품에 대한 "재판매 알림" 성격의 찜 기능이 필요해질 때.

#### ProductLike-008. UC-2 응답도 `isDuplicatedRequest`를 사용한다
- **일시**: 2026-08-25
- **결정**: 좋아요 취소(UC-2)의 응답 바디를 UC-1과 동일한 `memberId` / `productId` / `isDuplicatedRequest` 3필드로 한다. 갱신된 좋아요 수는 포함하지 않는다.
- **이유**:
    - 플래그의 의미를 "이 요청이 상태를 바꿨는가"로 통일하면 등록과 취소에 똑같이 적용된다
    - 클라이언트가 두 응답을 같은 형태로 다룰 수 있다. 필드명이 갈리면 분기 코드가 생긴다
    - 좋아요 수를 빼는 이유는 UC-1과 같다 — 카운트가 필요하면 상품 조회로 받는다
- **영향**:
    - `isAlreadyUnliked` 같은 취소 전용 이름을 쓰지 않는다
    - 결과가 "변경됨 / 변경 안 됨" 두 가지를 넘어서면 enum 도입을 재검토한다
- **관련 결정**: ProductLike-001(멱등 처리)

#### ProductLike-009. 좋아요 제거는 Repository가 수행한다
- **일시**: 2026-08-25
- **결정**: 엔티티에 `unlike()` 메서드를 두지 않는다. 삭제는 `ProductLikeRepository.delete(productLike)`가 담당한다.
- **이유**:
    - ProductLike-004가 Hard Delete를 정했는데, **엔티티가 자기 자신을 물리적으로 삭제할 수는 없다**
    - `BaseEntity.delete()`(soft delete)를 호출하게 두면 ProductLike-004와 어긋나고, 빈 메서드로 두면 역할이 모호해진다
    - 삭제는 영속성 관심사이므로 Repository의 책임이 맞다
- **영향**:
    - B.1 행위 목록에서 `unlike()`가 빠진다. 문서와 코드가 갈리던 지점을 정리한 것
    - 생성은 여전히 `ProductLike.like()` 정적 팩토리가 담당한다 (비대칭이지만, 생성에는 불변식 검증이 있고 삭제에는 없다)
- **관련 결정**: ProductLike-004(Hard Delete)

### C.2. 보류된 결정

#### 알아둘 것

- **회원 존재 검증을 하지 않는다.** UC-1에서 의도적으로 제거했고, 인증 레이어가 담당한다는 전제다.
  그런데 인증 레이어가 아직 없어서 `X-MEMBER-ID` 헤더에 아무 숫자나 넣으면 **존재하지 않는 회원의 좋아요가 생성된다.**
  `ProductLike.memberId`는 FK가 아닌 단순 `Long` 참조라 DB도 막지 않는다.
- 응답 바디의 `memberId` / `productId`가 올바른지는 어느 테스트도 검증하지 않는다.
  E2E는 `@GeneratedValue(IDENTITY)` 때문에 픽스처로 id를 지정할 수 없어, 두 값이 우연히 같아지면 뒤바뀜을 못 잡는다.
