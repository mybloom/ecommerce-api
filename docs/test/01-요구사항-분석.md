## 2. 테스트 대상 요약

### 2.1 결제 흐름

| 수단 | 흐름 | 최종 결과를 정하는 곳 |
|---|---|---|
| POINT | T0 접수(커밋) → T1 포인트 차감·승인·주문 `PAID` → 실패 시 T2 결제 `FAILED`·재고 복원·주문 `PAYMENT_FAILED` | 요청 안에서 끝난다 |
| CARD | 결제 `PENDING` 커밋 → PG 승인 요청 → `PENDING` 응답 | **PG 콜백** (UC-2) |

### 2.2 상태

| 대상 | 상태와 전이 |
|---|---|
| 주문 `OrderStatus` | `AWAITING_PAYMENT` → `PAID` / `PAYMENT_FAILED` (결제 흐름만 트리거, Payment-004) |
| 결제 `PaymentStatus` | `PENDING` → `APPROVED` / `FAILED`. 종결 후 전이 없음 |

### 2.3 의존 시스템: pg-simulator의 실제 동작

명세가 아니라 **코드에서 확인한 동작**이다. 시스템 테스트 설계와 결정성에 직접 영향을 준다.

| 구간 | 동작 | 근거 |
|---|---|---|
| 승인 요청 응답 | 100~500ms 지연, **40% 확률로 500** | `PaymentApi.kt` |
| 승인 처리 | 요청 1~5초 뒤 비동기 처리. 20% 한도초과, 10% 잘못된 카드, 70% 승인 | `PaymentEventListener.kt`, `PaymentApplicationService.kt` |
| 콜백 전송 | **한 번만 보낸다. 실패하면 로그만 남기고 재전송하지 않는다** | `PaymentCoreRelay.kt` |
| 결과 조회 | `transactionKey` 또는 `orderId`로 조회 가능 (`X-USER-ID` 필요) | `PaymentApi.kt` |

## 3. 질의 목록

> - **상태**: ✅ 문서·코드로 답을 확인함 / ❓ 미결 (PO·개발에 질의) / ⚠️ 가설 (테스트로 검증해야 함)
> - **테스트 방법** : 해당 질의를 위해 어떤 테스트를 만들어야 하는 지 작성. Day 2 테스트 설계의 입력이 된다.

### A. 결제 요청 (UC-1)

| ID | 질의 | 상태 | 확인한 답 / 근거 | 테스트 방법                                                        |
|---|---|---|---|--------------------------------------------------------------|
| Q-A1 | 결제 금액은 어디서 오는가? 요청에 금액을 넣으면? | ✅ | 주문 총액을 복사한다. 요청 DTO에 금액 필드가 없다 (Payment-002) | 요청에 `amount`를 추가로 실어도 무시되는지 API 테스트                          |
| Q-A2 | 같은 주문에 동시에 결제를 두 번 요청하면? | ✅ | `orderId` UNIQUE로 한 건만 남고 두 번째는 409 (Payment-001). **UseCase 레벨 동시성 테스트만 있다** | HTTP 레벨 동시 요청 테스트                                            |
| Q-A3 | 같은 회원이 **서로 다른 주문 두 개**를 동시에 포인트로 결제하면? | ⚠️ | 포인트를 `findByMemberId`로 **잠금 없이** 읽고, `Point`에 `@Version`도 없다. 두 트랜잭션이 같은 잔액을 읽고 각자 차감해 커밋하면 **한 번의 차감이 사라진다(lost update).** 기존 동시성 테스트는 같은 주문만 다뤄 UNIQUE가 막아 주었다 | 다른 주문 동시 결제 → 차감 총액 = 결제 총액 검증 (Day 3 최우선)                   |
| Q-A4 | `PAYMENT_FAILED` 주문을 다시 결제할 수 있는가? 실패 사유가 "다른 카드를 선택해주세요"인데? | ✅ | 불가. UNIQUE에 막힌다. 안내 문구와 실제 가능한 행동이 어긋난다고 문서가 인정함 (Payment-009, C.2) | 재결제 시 409 확인 + **제품 리스크로 보고**                                |
| Q-A5 | 카드 결제가 `PENDING`으로 끝났을 때 사용자는 결과를 어떻게 아는가? | ✅ | 명세는 주문 상세 조회(`GET /api/v1/orders/{orderNumber}`)를 폴링한다고 한다 (Payment-007, 06_order.md UC-3). 주문 API는 `POST`만 구현되어 있고, **이번 범위에서는 미구현으로 남기기로 결정했다.** 사용자가 카드 결제 결과를 확인할 경로가 없다 | E2E는 결과를 DB 조회 또는 PG 조회(`orderId`)로 확인한다. 사용자 확인 경로 부재는 **남은 리스크**로 기록 |
| Q-A6 | PG 결과를 모르는(`PgResultUnknown`) 결제는 언제 정리되는가? | ✅ | 대사 배치가 맡는데 **미구현**이고, 이번 범위에서 구현하지 않기로 결정했다. 그동안 결제 `PENDING`, 재고 묶임, 재결제 불가 (C.2) | 영구 `PENDING` 체류를 **남은 리스크**로 기록. 시뮬레이터 40% 500 때문에 실제로 자주 발생 |

### B. PG 콜백 (UC-2)

| ID | 질의 | 상태 | 확인한 답 / 근거 | 테스트 영향 |
|---|---|---|---|---|
| Q-B1 | 콜백이 결제 요청 응답보다 먼저 도착하면? | ✅ | PG 호출 전에 `PENDING`을 커밋하므로 처리 가능 (UC-1). **실제 비동기 흐름으로 검증한 테스트는 없다** | 시스템 테스트에서 콜백 지연 0에 가깝게 재현 |
| Q-B2 | 같은 콜백이 **동시에** 두 번 오면? | ⚠️ | 순차 중복은 테스트됨. 코드 주석은 "한 트랜잭션이라 안전"이라 하지만, 결제·주문 조회에 **잠금이나 `@Version`이 없다.** 두 트랜잭션이 함께 `PENDING`을 읽으면 **재고가 두 번 복원될 수 있다** | 동시 콜백 통합 테스트 (Day 3 최우선) |
| Q-B3 | `SUCCESS`와 `FAILED` 콜백이 동시에 오면? | ⚠️ | Q-B2와 같은 이유로 결제는 승인인데 재고는 복원되는 등 상태가 어긋날 수 있다 | 동시 상반 콜백 통합 테스트 |
| Q-B4 | 콜백 처리가 실패해 5xx를 주면 PG가 다시 보내는가? | ⚠️ | 명세는 "5xx면 PG가 재전송한다"를 전제로 한다 (Payment-005). **pg-simulator는 재전송하지 않는다.** 실제 PG의 재전송 정책도 문서에 없다 | 의존 시스템 가정 불일치로 보고. 콜백 실패 시 결제가 `PENDING`에 남는지 시스템 테스트 |
| Q-B5 | **누가 콜백을 보낼 수 있는가?** | ⚠️ | 콜백 엔드포인트에 인증·서명·IP 제한이 없다. 대상은 `orderNumber`로만 특정하고, 금액 대조만 한다. 사용자는 자기 주문 금액을 알므로 **위조 `SUCCESS` 콜백으로 카드 결제 주문을 `PAID`로 만들 수 있다** | 위조 콜백 보안 테스트 (Day 3 최우선) |
| Q-B6 | 콜백의 `transactionKey`가 PG에 실제로 있는 거래인지 확인하는가? | ✅ | 확인하지 않는다. 받은 값을 그대로 저장한다 | Q-B5와 함께 검증 |
| Q-B7 | 콜백이 아예 오지 않으면? | ✅ | 결제 `PENDING`, 주문 `AWAITING_PAYMENT`에 영구 체류. 정리 주체 없음 (C.2) | 남은 리스크로 기록 |

## 4. 명세와 실제가 어긋나는 지점 (핵심 발견)

요구사항 분석 단계에서 코드를 함께 읽어 찾은 것이다. **Day 3에 테스트로 확인한 뒤** 버그 이슈로 등록한다. 단, 미구현 유지로 결정한 F-4·F-7은 등록 대상에서 빠지고 남은 리스크로 기록한다.

| ID | 발견 | 근거 질의 | 예상 Severity | 왜 중요한가 |
|---|---|---|---|---|
| F-1 | **콜백 위조로 결제 없이 주문이 `PAID`가 될 수 있다** | Q-B5, Q-B6 | Critical | 돈을 받지 않고 상품이 나간다 |
| F-2 | **동시 콜백이 재고를 두 번 복원할 수 있다** | Q-B2, Q-B3 | Major | 재고 정합성이 깨진다. 코드 주석이 안전하다고 적고 있어 리뷰로도 놓치기 쉽다 |
| F-3 | **명세는 PG 재전송을 전제하지만 연동 대상은 재전송하지 않는다** | Q-B4 | Major | 콜백 처리가 한 번 실패하면 결제가 영구 `PENDING`. 실제 PG의 재전송 정책 확인이 필요 |
| F-4 | 결과를 모르는 결제의 정리 수단이 없고, 연동 대상에서 40% 확률로 발생한다 | Q-A6, Q-B7 | Major (알려진 이슈, 미구현 유지) | 재고가 묶이고 재결제가 막힌다 |
| F-5 | 실패 안내("다른 카드를 선택해주세요")와 실제 가능한 행동(재결제 불가)이 어긋난다 | Q-A4 | Minor (알려진 이슈) | 고객 경험·CS 리스크 |
| F-6 | **같은 회원이 다른 주문을 동시에 포인트로 결제하면 차감이 한 번 사라질 수 있다** | Q-A3 | Critical | 포인트를 덜 받고 두 주문이 결제완료된다. 돈이 직접 새는 결함 |
| F-7 | 주문 상세 조회 API가 명세에만 있고 구현되지 않았다 | Q-A5, Q-E3 | — (미구현 유지 결정) | 사용자가 카드 결제 결과를 확인할 수 없다. 테스트도 결과를 API로 관측하지 못한다 |

> F-4, F-5는 개발 문서(C.2)가 이미 알고 있는 이슈다. 새로 찾은 결함은 F-1~F-3, F-6이다. F-1·F-2·F-3·F-6은 **단위 테스트나 Mock 기반 테스트로는 드러나지 않는다** — 실제 동시성, 실제 의존 시스템 동작, 공격자 관점이 필요하다. SDET 관점 테스트가 보강해야 하는 지점이 여기다. F-7은 명세와 구현을 대조해 찾았고, 미구현으로 두기로 결정했다.

## 5. 요구사항 ID (RTM 기준)

> 1절에서 정한 분석 범위 안의 명세를 한 문장씩 나눠, 각 요구사항이 **검증 가능한 문장 하나**가 되게 적는다. 요구사항과 테스트는 1:1로 연결한다.
> - 명세에 답이 없는 항목은 요구사항으로 단정하지 않고 3절 질의로 확인한다
> - 명세와 코드를 대조해 두 종류를 함께 뽑는다
>   - **명세에 없지만 있어야 하는 것** — 예: REQ-PAY-13(콜백 출처 검증), REQ-PAY-14(동시 포인트 결제의 차감 총액)
>   - **명세에는 있지만 구현이 없거나 암묵적인 것** — 예: REQ-PAY-15(주문 상세 조회)

| ID | 요구사항 | 출처 |
|---|---|---|
| REQ-PAY-01 | 포인트로 결제하면 즉시 승인되고 주문이 결제완료된다 | UC-1 POINT |

### 6.2 인수 조건 (초안)

```gherkin
Feature: 결제완료 주문 취소

  Scenario: 포인트로 결제한 주문을 취소하면 포인트와 재고가 돌아온다
    Given 포인트 10,000원으로 결제완료된 주문이 있다
    When 주문을 취소한다
    Then 주문은 취소 상태가 된다
    And 포인트 잔액이 10,000원 늘어난다
    And 주문한 수량만큼 재고가 복원된다

  Scenario: 카드로 결제한 주문을 취소하면 PG 승인이 취소된다
    Given 카드로 결제완료된 주문이 있다
    When 주문을 취소한다
    Then PG에 승인 취소가 요청된다
    And 주문은 취소 상태가 되고 재고가 복원된다

  Scenario: PG 취소 결과를 알 수 없으면 취소를 확정하지 않는다
    Given 카드로 결제완료된 주문이 있다
    And PG 취소 요청이 응답 없이 시간 초과된다
    When 주문을 취소한다
    Then 주문은 취소 확정 상태가 아니다
    And 재고와 포인트는 바뀌지 않는다

  Scenario: 같은 주문에 취소를 동시에 두 번 요청해도 한 번만 처리된다
    Given 포인트로 결제완료된 주문이 있다
    When 같은 주문에 취소를 동시에 두 번 요청한다
    Then 한 요청만 성공하고 다른 요청은 409를 받는다
    And 포인트와 재고는 한 번만 복원된다

  Scenario: 이미 취소된 주문은 다시 취소할 수 없다
    Given 취소된 주문이 있다
    When 주문을 취소한다
    Then 409를 받는다
```
