| **METHOD** | **URI**              | **설명** |
| --- |----------------------| --- |

>

> 📋 `X-MEMBER-ID` 는 회원가입 시 가입한 ID 입니다.

# 1. "e-상점 도메인" 설명

- 상점에서 물건을 구매하기 위해서는 회원으로 등록해야 한다.
    - 다만, 회원이 되기 전에도 상점에 대한 소개와 상품 정보를 살펴볼 수 있다.
    - 상품을 구매하기 위해서는 등록을 완료하고 활동 가능한 회원이 되어야 한다.
    - 회원 등록이 완료되면 0포인트를 얻는다.
    - 등록을 완료한 회원은 프로필 주소와 자기 소개를 조회할 수 있다.
    - 회원가입은 ID 및 성별, 생년월일, 이메일 주소를 받습니다.
    - 회원의 등록 시간을 저장한다.
- 상점은 사전 충전된 포인트를 사용하여 상품을 결제하는 구조를 가진다.
    - 포인트는 회원만 충전할 수 있다.
    - 포인트 충전은 별도의 충전 요청을 통해 수행된다.
    - 회원은 현재 보유 중인 포인트 잔액을 조회할 수 있다.
    - 상품 주문 시 포인트는 자동으로 차감된다.
        - 포인트 사용을 위한 별도의 API는 제공하지 않는다.
        - 포인트 차감은 주문 처리의 일부로 함께 수행된다.
    - 보유 포인트가 부족한 경우 상품 구매는 실패한다.
    - 포인트 충전 및 차감 내역은 시스템에서 관리된다.

# 2. 애그리거트

# 2.1 멤버 애그리거트
## (1) 멤버 (Member) : Entity 
### 속성
- `id`: `Long`
- `loginId`: 회원 ID (외부 식별자, X-USER-ID로 사용)
- `passwordHash` : 비밀번호 
- `gender`: 성별
- `birthDate`: 생년월일
- `email`: 이메일
- `registeredAt`: 회원 등록 시간

### 행위
- `constructor` : 회원 생성: userId, passwordHash, gender, birthDate, email
  - 도메인 관점에서 비밀번호 해시로 만들어서 저장되고 그거를 해시를 이용해서
- `static register()` : 회원 가입: userId, gender, birthDate, email
    - 가입 완료 시 포인트는 0으로 초기화된다.
- `toProfile()` : 회원 프로필 조회
- `verifyPassword()` : 비밀번호를 검증한다.

>#### passwordHash: 도메인 내부에서 처리
>- 비밀번호 → 해시 변환을 도메인 책임으로 둠
>- 패스워드 해싱은 외부에서 처리해서 넘길 게 아니라 도메인 로직으로 보고 내부에서 다룬다. 
>- 이를 위해 PasswordEncoder 같은 별도 구성 요소를 도입.


### 규칙
- 회원이 아니어도 상점에 대한 소개와 상품 정보는 조회할 수 있다
- 상점에서 물건을 구매하기 위해서는 회원으로 등록해야 한다.
- 회원 가입 시 loginId, 성별, 생년월일, 이메일 주소를 필수로 입력받는다.
- loginId, email은 중복될 수 없다.
- 회원 등록이 완료되면 보유 포인트는 0포인트로 설정된다.
- 등록을 완료한 회원만 자기 정보를 조회할 수 있다.
- 회원의 비밀번호는 해시를 만들어서 저장한다.

## (2) 비밀번호 인코더(PasswordEncoder) : Domain Service
- 도메인 안에 소속되어 있지만 특정 엔티티 안에 집어넣기가 애매한 기능
- 상세한 구현은 굳이 도메인에 담아 둘 필요가 없는 것들
- "어떤 일을 한다" 정도만 인터페이스로 정의하면 되는 것을 도메인 서비스라고 부르기로 한다. 

>#### 패스워드 인코딩 기능 -> 기술적 관심사
>1. 패스워드 인코딩 기능을 엔티티 내부에 직접 구현하는 방식은 지양한다.
>   - 암호화 방식은 다양하고 계속 변화하기 때문에 이는 기술적인 관심사에 가깝다.
>   - 이러한 기술적인 로직이 도메인 코드에 직접 드러나면 도메인의 순수성과 가독성이 떨어진다.
>   - 따라서 비밀번호 해싱 역할은 도메인 요소로 추상화(“비밀번호를 해싱한다”는 행위 자체는 도메인에 속하지만)하되, <br>
>   구현은 인터페이스로 분리(구체적인 해싱 방식 구현은 외부에서 주입받도록 설계)한다. 
>2. 해당 인터페이스는 도메인에 두지 않고 외부 계층에 둔다.   
>   - 인터페이스를 외부 계층에 두면 도메인 모델이 기술적인 구현 세부사항에 의존하지 않게 되어, 도메인의 순수성을 유지할 수 있다.

### 행위
- `encode()` : 비밀번호 암호화하기
- `matches()` : 비밀번호가 일치하는지 확

## (3) Email : Value Object

> #### Value Object
>- 값 객체는 도메인 모델의 핵심 구성 요소로 값 그 자체의 의미를 담아내고
   불변성, 동등성 등의 도메인 로직을 포함하여 설계하는 방식
>- 도메인 모델에서 식별자가 필요하지 않고 속성/값으로만 구별되는 오브젝트
>- 특징
>  - 엔티티가 너무 많은 책임을 가지는 것을 방지하고 특정 속성 관련 행위를 분리해서 엔티티를 더 집중된 상태로 유지하게 한다
>  - 원시 타입보다는 도메인 개념을 더 명시적으로 나타내서 모델의 명확성을 높인다
>  - 생성 이후에 상태가 변하지 않고 변경이 필요하면 새로운 객체로 교체한다
>  - 풍부한 기능을 가진다
>  - 자체 유효성 검사도 가능하다
>  - 개념에 포함된 여러 개의 속성을 가질 수 있다

# 2.2 포인트 애그리거트
## (1) 포인트 Point : Entity
### 속성
- `id`: `Long`
- `userId`: `Long` 포인트 소유 회원 ID
- `balance`: `PointAmount` 보유 포인트 잔액
- `createdAt`: 포인트 생성 시간
- `updatedAt`: 포인트 변경 시간

### 행위
- `static create()` : 포인트 생성
    - 회원 등록 시 포인트를 생성한다.
    - 초기 포인트 잔액은 0으로 설정된다.
- `charge(amount)`: 포인트 충전. 1이상 충전 가능.
- `use(amount)`: 포인트 차감. 0이상 차감 가능. 보유 포인트보다 같거나 작은 양만 차감 가능.
- `currentBalance()` : `Long` 현재 보유 중인 포인트 잔액 조회.

### 규칙
- 상점은 사전 충전된 포인트를 사용하여 상품을 결제하는 구조를 가진다.
- 포인트는 회원만 소유할 수 있다.
    - 회원 등록이 완료되면 포인트가 생성되며, 초기 잔액은 0포인트이다.
- 포인트 충전은 별도의 충전 요청을 통해 수행된다.
    - 충전은 1포인트 이상 가능하다.
- 상품 주문 시 포인트는 자동으로 차감된다.
    - 포인트 사용을 위한 별도의 API는 제공하지 않는다.
    - 포인트 차감은 주문 처리 과정의 일부로 함께 수행된다.
    - 포인트 잔액은 0 미만이 될 수 없다.
    - 보유 포인트가 부족한 경우 상품 구매는 실패한다.
- 회원은 자신의 포인트 잔액을 조회할 수 있다.

## (2) PointAmount  : Value Object
### 속성
- `value` : `Long` 값
### 행위
- `PointAmount()` : 포인트어마운트 생성. 0이상 허용
- `increase()` : 포인트 증가. 1이상 허용
- `decrease()` : 포인트 감소. 기존 포인트보다 같거나 작어야 가능.
