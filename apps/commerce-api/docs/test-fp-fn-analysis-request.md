# 테스트 코드 분석 요청: 구조적 False Positive / False Negative 지점 탐색

## 1. 분석 대상 및 배경

### 1.1 분석 대상
- **대상**: 프로덕션 코드가 아니라 **테스트 코드 자체**
- **목적**: 테스트가 비즈니스 요구사항을 제대로 검증하고 있는지, 구조적으로 FP/FN을 유발할 수 있는 지점은 어디인지 파악
- **분석 범위**: `commerce-api` 모듈 및 관련 모듈 전체의 테스트 코드 (`src/test`, `testFixtures` 모두 포함)

### 1.2 시스템 도메인

이 프로젝트는 **이커머스 백엔드**입니다. 핵심 도메인은 다음과 같습니다:

#### 멤버 (Members)
- 회원가입 (LoginID, 성별, 생년월일, 이메일, 패스워드)
- 내 정보 조회
- 인증/인가는 구현 범위 밖. `X-MEMBER-ID` 헤더로 사용자 식별
- 엔드포인트: `POST /api/v1/members`, `GET /api/v1/members/me`

#### 포인트 (Points)
- 실제 PG 결제가 아니라 **사전 충전된 포인트로 상품을 결제**하는 구조
- 포인트 충전, 보유 포인트 조회
- 포인트 사용은 별도 API가 없고 **주문 처리 흐름 내에서 자동 차감**됨
- 엔드포인트: `POST /api/v1/points/charge`, `GET /api/v1/points`

#### 주문/쿠폰 (도메인 설명에서 언급됨)
- 사용자는 쿠폰을 발급받고 여러 상품을 한 번에 주문/결제

### 1.3 모듈 및 패키지 구조

`commerce-api` 내부는 헥사고날/클린 아키텍처 스타일로 구성되어 있습니다.

```
com.loopers
├── interfaces.api.*        # Controller (HTTP 계층)
├── application.*           # UseCase (오케스트레이션 + 트랜잭션 경계)
├── domain.*                # 도메인 객체, Service, Repository 인터페이스
├── infrastructure.*        # JPA repository 구현체
└── support.error           # CoreException, ErrorType
```

데이터 흐름: `interfaces → application → domain ← infrastructure`

요청 흐름:
```
Request DTO → toInfo() → UseCaseDto.Info
  → UseCase.method() → ServiceDto.Command
  → DomainService.method() → 도메인 객체 / ServiceDto.Query
  → UseCaseDto.Result.from()
  → Response DTO.from()
  → ApiResponse.success(...)
```

각 계층은 자체 DTO 컨테이너(`XxxV1Dto`, `XxxUseCaseDto`, `XxxServiceDto`)를 가지며, 변환은 아래로는 `toInfo()` / `toCommand()`, 위로는 `from()`으로 이루어집니다.

별도 모듈로 `modules/jpa`가 존재하며 테스트 픽스처(`DatabaseCleanUp` 등)를 제공합니다.

### 1.4 테스트 컨벤션 (이 프로젝트의 기존 규칙)

분석 시 다음 컨벤션을 **"일탈 = 즉시 의심"의 기준**으로 활용해 주세요. 컨벤션을 벗어난 테스트는 FP/FN의 원인일 가능성이 높습니다.

| 테스트 클래스 유형 | 어노테이션 | 목적 |
|---|---|---|
| 도메인 객체 테스트 | 순수 JUnit (Spring 미사용) | 엔티티/VO 동작에 대한 단위 테스트 |
| 도메인 서비스 테스트 | `@ExtendWith(MockitoExtension.class)` | repository에 Mockito mock 사용. 수동 생성자 주입 (`@InjectMocks` 절대 사용 금지) |
| UseCase 테스트 | `@SpringBootTest` | Testcontainers를 통한 전체 Spring 컨텍스트 + 실제 DB. 롤백 테스트를 위해 부분적 실패를 강제할 때는 `@MockitoSpyBean` 사용 |
| Controller 슬라이스 테스트 | `@WebMvcTest` | HTTP 계약(`@Valid`, 헤더, 라우팅) 검증. UseCase는 `@MockitoBean` 처리 |
| E2E 테스트 | `@SpringBootTest(RANDOM_PORT)` | `TestRestTemplate`을 사용한 풀 스택 테스트. `@BeforeEach`에서 repository 직접 셋업 |

추가 규칙:
- 모든 통합/E2E 테스트는 `@AfterEach`에서 `databaseCleanUp.truncateAllTables()` 호출
- 픽스처 클래스는 `XxxFixture`로 명명, `a-`/`an-` 접두사 팩토리 메서드 사용 (예: `aPointWithBalance(1000L)`)
- 픽스처 위치: 앱의 `src/test` 
- 예외 단언은 항상 메시지 부분 문자열이 아니라 **`ErrorType` enum**(컴파일 안전)을 검증
- Mockito는 `when().thenReturn()` (classic) 스타일로 통일. BDD `given().willReturn()`과 섞지 않음

### 1.5 우려되는 시나리오
- 특별히 의심하는 지점은 없음. 균형 있게 전체를 봐주세요.
- 다만 일반적으로 **FN(버그가 있는데 테스트가 통과)**이 FP보다 위험도가 높으니, 동등한 강도로 보되 FN 쪽을 약간 더 비중 있게 봐주세요.

## 2. 판정 기준 (참고 자료)

> **중요**: 아래 글은 FP/FN을 정의하는 **렌즈**로만 사용하세요.
> 이 글 자체를 분석하거나 이 글에 나온 코드를 찾으려 하지 마세요.
> 1번에서 지정한 테스트 코드를, 아래 정의에 따라 분석해 주세요.

### 핵심 요약 (먼저 읽을 것)

테스트 코드를 분석할 때:
- **False Positive (FP)** = 프로덕션 코드는 정상인데 테스트가 실패하는 경우 (= 거짓 경보, flaky, 잘못된 단언, 구현 디테일에 과결합)
- **False Negative (FN)** = 프로덕션 코드에 버그가 있는데 테스트가 통과하는 경우 (= 검증 누락, mock 과다, 약한 단언, 엣지 케이스 미커버)

`positive`는 "긍정적"이 아니라 **"양성 반응 = 테스트가 무언가를 잡아냈다고 주장하는 것"**입니다. 테스트가 실패할 때가 positive입니다.

### 참고 글 본문: 소프트웨어 테스팅의 False Positive

False Positive는 이진 분류(binary classification) 실험 오류 중 하나로 통계 실험에서는 1종 오류(Type I Error)라고도 부르며 소프트웨어 테스팅에서도 쓰이는 용어다. 하지만 이진 분류와 통계 실험에 대한 배경지식이 없는 경우 소프트웨어 테스팅의 False Positive는 본래의 뜻과 반대의 의미로 잘못 사용되곤 한다. 언어가 잘못 사용되면 당연히 의사소통 장애로 이어진다.

False Positive의 'positive'를 '긍정적'으로 이해하면 이런 문제가 발생한다. 고민할 것 없이 'false'는 '거짓'이고 테스트 케이스의 성공은 프로그래머 입장에서 긍정적인 결과이니, False Positive를 테스트 케이스가 버그를 잡아내지 못하고 성공하는 상황이라 생각하는 것이다. 안타깝게도 이것은 완전히 오해다.

False Positive의 'positive'는 '양성'을 뜻한다. 테스트 케이스에게 양성반응이란 단언(assertion)이 참이라는 가설(귀무가설, null hypothesis)을 기각하고 프로그래머에게 '이봐, 내가 뭔가 발견했어!'라고 알려주는 것이다. 쉽게 말해 테스트 케이스 실패다. 그러니까 소프트웨어 테스팅에서 False Positive는 대상 코드가 정상이지만 테스트 케이스가 실패하는 경우를 뜻한다.

|              | 테스트 실패         | 테스트 성공         |
|--------------|---------------------|---------------------|
| 비정상 코드  | 참 양성(TP)         | 거짓 음성(FN)       |
| 정상 코드    | 거짓 양성(FP)       | 참 음성(TN)         |

비슷하게 코드 분석기가 문제 없는 코드를 지적하는 것 역시 False Positive라고 부를 수 있다.

False Alarm이 False Positive와 동의어라는 것을 기억하면 False Negative(Type II Error)와의 혼동을 피할 수 있을 것이다. 테스트 케이스는 실패할 때 우리에게 경보(alarm)를 준다. 만약 이 경보가 거짓이라면 False Positive라는 용어로 상황을 표현할 수 있다.

## 3. 요청 사항

### 3.1 분석 작업

위 2번의 정의에 따라, 1번에서 지정한 테스트 코드 범위에서 **구조적으로 FP 또는 FN이 발생할 수 있는 지점**을 찾아주세요.

"구조적으로"의 의미는 단순한 오타나 일회성 실수가 아니라, **테스트 설계 자체의 문제로 특정 부류의 버그를 영구적으로 놓치거나 잘못된 실패를 만들어내는 패턴**입니다.

#### 특히 주의 깊게 봐야 할 패턴

**FN(버그를 놓침) 유발 패턴**:
- **지나친 mocking**: 도메인 서비스 테스트에서 핵심 로직까지 mock으로 가려서 실제 검증이 일어나지 않는 경우
- **약한 단언**: `assertNotNull`, `assertTrue(result.size() > 0)` 같은 헐거운 검증. 핵심 필드/상태 변화를 검증하지 않음
- **Happy path만 존재**: 정상 케이스만 있고 경계 조건/실패 케이스 누락 (예: 포인트 잔액 부족, 음수 충전, 동시 차감 등)
- **`ErrorType` 검증 누락**: 예외 발생만 검증하고 어떤 `ErrorType`인지 검증하지 않음 → 다른 종류의 예외가 던져져도 통과
- **상태 검증 누락**: UseCase 테스트에서 반환값만 보고 DB 상태나 부수 효과(side effect)를 검증하지 않음
- **트랜잭션 롤백 미검증**: 부분 실패 시나리오에서 `@MockitoSpyBean`으로 실패를 주입했지만, 실제로 롤백이 일어났는지 DB 상태로 확인하지 않음
- **컨벤션 일탈로 인한 검증 약화**: `@SpringBootTest`로 해야 할 UseCase 테스트가 mock 단위 테스트로 작성되어 트랜잭션 경계가 검증되지 않는 경우
- **테스트 데이터의 우연한 통과**: 픽스처 값이 우연히 검증 로직과 맞아떨어져서, 다른 입력에선 실패할 코드가 통과하는 경우

**FP(거짓 경보) 유발 패턴**:
- **구현 디테일 결합**: 메서드 호출 횟수/순서를 너무 엄격하게 검증해서 리팩터링만 해도 실패
- **시간 의존성**: `LocalDateTime.now()` 직접 사용으로 인한 flakiness
- **순서 의존성**: 테스트 간 격리 실패 (DB 클린업 누락, 정적 상태 공유)
- **불필요한 정확 매칭**: 메시지 문자열 매칭 (컨벤션상 `ErrorType` 검증해야 하는데 메시지로 검증)
- **외부 환경 의존**: Testcontainers 외부 리소스, 네트워크, 파일 시스템 등에 대한 가정

**계층별 점검 포인트**:
- **Controller 슬라이스 테스트**: HTTP 계약(`@Valid`, 헤더 누락, 라우팅)만 검증해야 하는데 비즈니스 로직까지 검증하려 하지 않는지. `X-MEMBER-ID` 헤더 누락 케이스가 있는지
- **UseCase 테스트**: 실제 DB로 트랜잭션 경계와 부수 효과를 검증하는 본래 목적을 살리고 있는지. mock으로 회피하지 않는지
- **도메인 서비스 테스트**: repository만 mock하고 도메인 로직은 실제로 실행되는지. 도메인 로직까지 mock으로 가리지 않는지
- **도메인 객체 테스트**: Spring 없이 순수하게 엔티티/VO 동작을 검증하는지. 불필요하게 Spring을 끌어오지 않는지
- **E2E 테스트**: `@BeforeEach` repository 셋업이 의도한 사전 상태를 정확히 만들어내는지

### 3.2 출력 형식

각 지점마다 다음 형식으로 정리해주세요:

```
### [번호]. [짧은 제목]
- **위치**: `파일경로:라인번호` (또는 클래스/메서드 단위)
- **테스트 계층**: 도메인 객체 / 도메인 서비스 / UseCase / Controller 슬라이스 / E2E
- **유형**: FP / FN / 둘 다 가능
- **원인**: 어떤 테스트 설계가, 왜 오판을 유발하는지 (구조적 관점에서 설명)
- **놓칠 수 있는 버그 시나리오**: 이 테스트가 통과하는데도 살아남을 수 있는 실제 버그의 구체적인 예 (FN인 경우) / 정상 코드를 어떻게 실패시킬 수 있는지 (FP인 경우)
- **영향도**: 낮음 / 중간 / 높음 (그렇게 본 이유 한 줄)
- **개선 방향**: 구체적인 수정 아이디어. 가능하면 코드 스니펫 포함
```

### 3.3 정렬 및 추가 요청

- **영향도가 높은 순**으로 정렬
- 분석 마지막에 **전체 요약** 섹션을 두고, 발견된 패턴의 공통점이 있다면 정리 (예: "전반적으로 UseCase 테스트에서 DB 상태 검증이 약함", "ErrorType 검증보다 메시지 검증이 많음" 등)
- **컨벤션 일탈 목록**을 별도 섹션으로 정리 (1.4의 규칙을 어기는 테스트들)
- 확신이 낮은 추측은 별도로 **"추가 검토 필요"** 섹션에 분리
- 분석 대상 코드를 읽어본 결과 1번의 배경 설명과 다른 점이 보이면 분석 시작 전에 먼저 알려주세요 (잘못된 전제로 분석하지 않도록)
- **테스트가 아예 없는 영역**이 있다면 별도 섹션으로 알려주세요 (이것도 일종의 FN입니다 — 테스트 자체가 없으니 어떤 버그도 잡지 못함)
